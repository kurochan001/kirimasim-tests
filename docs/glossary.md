# kirimasim-testsの用語集

このテストスイートのREADME、テストのヘッダ、実行結果、網羅率の資料で使う用語を、役割ごとにまとめています。運用上の疑問は[FAQ](faq.md)、全体の入口は[README](../README.md)を参照してください。

ここでいう「設計網羅率」「実行確認率」は、このリポジトリの要求台帳と計測規則に基づく指標です。シミュレータの画面にあるカバレッジや、Nightlyの一致率とは分母が異なります。

## 1. テストの基本

| 用語 | 意味・このスイートでの使い方 |
| --- | --- |
| SystemVerilog／IEEE 1800-2023 | 検査対象のハードウェア記述・検証言語／このスイートが期待結果の根拠にする規格の版 |
| LRM（Language Reference Manual）／節・条文 | 言語規格の呼び方／動作や制約を定めた箇所。`:lrm:`に節番号を記録する |
| 適合テスト（conformance test） | シミュレータの動作が規格の定める結果になるかを調べる試験。このスイートでは小さな設計と期待結果を組にする |
| 刺激／観測点 | 狙った条件を作る入力や操作／結果として確認する値・メッセージ・時点。入力を与えただけでは結果の確認にならない |
| 期待結果／期待出力 | 合格とする値や拒否・終了の条件／そのうち標準出力として比較する文字列。`.expected`は期待出力を保存するファイル |
| 正常系／違法系（illegal design） | 合法な設計の動作を確認するテスト／規格違反を含み、適切なエラーで拒否されることを確認するテスト |
| ランナー（runner） | テストのヘッダを読み、ビルド・実行・出力比較を行う`tools/run_*.py`。シミュレータごとに用意する |
| 正規化（normalization） | 空行やツール固有の終了表示などを比較対象から除く処理。文字のある行の空白・桁・値はそのまま比較する。除去する診断やバナーはランナーごとに決めている |
| 標準出力／標準エラー／終了コード | 設計が表示した結果、シミュレータの診断、プロセスの終了状態。テストが指定する条件に応じてそれぞれを検査する |

参照：[テスト形式](../README.md#test-format)、[判定方法](../README.md#how-a-test-is-judged)、[テストカタログ](tests/README.md)。

## 2. メタデータと期待値の根拠

| 用語・フィールド | 意味・確認すること |
| --- | --- |
| メタデータ（metadata） | `.sv`の先頭コメントにある`:name:`などの項目。目的、規格根拠、実行方法、判定条件を記録する |
| sv-tests互換 | 他の言語テスト集でも使われるヘッダ形式に合わせていること。このスイート独自の項目もある |
| `:lrm:` | 検査する規格の節番号。節を引用していることと、その節の全要求を検査できることは分けて確認する |
| oracle（オラクル）／`:oracle:` | 期待結果の根拠／規格との照合や、期待結果を確認した固定版シミュレータを記録する項目 |
| `spec`／standard only | 引用条文に基づく期待結果／`:oracle:`が`spec`だけの状態。固定版シミュレータによる確認を記録していない |
| `iverilog@13.0`／`verilator@5.052` | その固定版で期待結果を確認したという記録。Nightlyで使う開発版や、別のリリースへ自動で読み替えない |
| `:spec_check:` | 規格と期待結果を照合した主体。`ai`はAIによる確認、`human`は人による確認を表す |
| `:fourstate:` | 結果がX/Zに依存するか。`yes`のテストを2値の実行だけで同等に確認したとは扱わない |
| `:expected_stdout:`／`:should_fail_because:` | 期待する標準出力／違法設計を拒否すべき理由。違法系には期待出力ではなく診断の条件を記録する |
| `:expected_stderr_regex:`／正規表現 | 診断を照合するパターン。適切な位置と、必要に応じて意図した違反の内容を検査する。構文未対応のエラーとの区別が必要 |
| `:files:`／`:incdirs:`／`:defines:` | 追加の入力ファイル／includeの検索先／コンパイル時のマクロ。テスト本体以外の再現条件にもなる |
| `:top_module:`／`:args:` | トップとして選ぶモジュールまたはconfig／実行時の引数。各ランナーがツールに合う形式へ変換する |

参照：[メタデータ一覧](../README.md#metadata)、[期待値の決め方](../README.md#where-the-expected-outputs-come-from)。

## 3. 結果とNightly

| 用語 | 意味・読み方 |
| --- | --- |
| Match／`pass` | 出力と、指定された終了・診断の条件が期待結果に一致したテスト。正しく拒否された違法系も含む |
| Differ／`fail` | テストの判定条件に合わない結果。出力差分、ビルド失敗、異常終了、違法設計の受理、診断条件の不一致などを含む |
| Known difference／`known` | Icarus・Verilatorの固定版oracleが付いていないテストの不一致。成功には数えず、その固定版の確認済みテストの回帰失敗とも分ける |
| Unsupported／`unsupported` | ランナーが認識する未対応機能の診断や、実行できない種類のテスト。未対応は成功には数えない |
| `NOW MATCHES` | Icarusランナーの表示。oracle未登録のテストが機械的な判定では一致したという意味で、oracle認定の自動追加ではない |
| Nightlyの一致率（match rate） | 同じ実行の一致したテスト数÷結果が記録された対象テスト数。Known differenceとUnsupportedも分母に含み、未対応として実行を省略したテストも含む。固定版ランナーの端末の要約とは集計範囲が異なる |
| Nightly | 開発版シミュレータ等で定期実行し、履歴・比較図を公開するGitHub Actionsのワークフロー |
| Check | 固定版oracleの再現、生成物、メタデータ、台帳、ツールの単体テストなどを検査するワークフロー |
| By chapter | 章ごとに各シミュレータの一致数／対象テスト数と一致率を並べる表。規格の要求ごとの網羅率ではない |
| 回帰（regression）／ratchet | 以前満たした条件が満たせなくなること／現在のNightlyでkirimasimの前回`pass`から今回`fail`への変化を失敗にする仕組み |
| `main`／`results`／suite commit | テストとツールを管理するブランチ／Nightlyの結果を公開するブランチ／その実行で使ったスイートのコミット |
| UTC／JST | 協定世界時／日本標準時。公開結果のUTC表示へ9時間を加えるとJSTになる |

参照：[Nightlyの見方](nightly-results.md)、[実行結果の形式](../tools/suite_results.py)、[ワークフロー](../README.md#workflows)。

## 4. 要求・照合・網羅率

| 用語 | 意味・計測の範囲 |
| --- | --- |
| 要求／要求ID | 規格が求める条件・動作・観測の登録単位／その識別子。1節に複数の要求があり得る |
| 要求台帳／`behaviors.json` | 要求の内容、合格基準、出典、確認に使うテストと観測点を管理する記録 |
| 出典監査（source review） | 規格の出典ブロックを調べ、要求・説明・例・参照等に分類して対応を記録すること。シミュレータでの実行確認とは別の工程 |
| 照合／レビュー済みの対応 | 要求をどのテストの刺激・観測で確認するかを結ぶこと／その内容をレビューして台帳へ登録した対応 |
| 引用カバレッジ／網羅深度 | どの節をテストが引用しているか／各節に何本の直接引用テストがあるか。条件・分岐・例外の検査範囲は別途確認する |
| 設計網羅率 | 観測点をレビューしたテスト対応がある登録要求数÷登録要求数。テストを設計・対応付けた範囲を示す |
| 実行確認率 | 現在の入力・ランナーに合う、採用可能な成功証跡がある登録要求数÷登録要求数。複数環境の成功の和集合を単一シミュレータの適合率とは扱わない |
| 暫定値／確定値／分母 | 登録行に基づく集計／解釈・重複・要求単位を整理し分母を承認した集計／割合の対象となる要求集合。現在の状態は集計概要で確認する |
| 解釈保留（interpretation issue） | 規格の読み方を確定できていない登録項目。暫定値の分母に残し、解決前にテスト対応を承認しない |
| 複合証拠／AND集合／`check_groups` | 1要求の条件を複数のテストで分担する対応。同じ実行回・環境で全メンバーが成功する必要がある。代替グループ間はOR |
| baseline（基準） | 要求や対応の削除・変更、複合証拠の変更などを検出するための記録。変更の根拠を確認して更新する |

参照：[集計概要](behavior-coverage-summary.md)、[計測規則](../coverage/README.md)、[要求からテストへの手順](requirements-to-tests-method.md)、[照合状況](test-requirement-matching.md)。

## 5. SVAと参照評価器

| 用語 | 意味・このスイートでの使い方 |
| --- | --- |
| SVA（SystemVerilog Assertions） | 条件や時間関係を記述する言語機能。このスイートでは、その評価・成功・失敗・アクション等の規格動作を検査する |
| 即時／並行アサーション | 手続きの実行時に条件を確認する記述／サンプリングイベントに沿って時間関係を評価する記述 |
| sequence／property（系列／性質） | 信号条件の並びや一致区間を表すもの／系列や時間演算などを組み合わせて評価する規則 |
| サンプル／tick | 特定のイベントで取り込んだ値／参照評価器でそのサンプリング時点を数える単位 |
| 前件・後件／空成功（vacuous pass） | 含意で要求の条件となる部分・要求される部分／前件不成立により後件の確認を要さず成功する場合 |
| Preponed／NBA／Reactive | 通常のクロック付き並行アサーションのサンプル値を採る領域／ノンブロッキング代入を更新する領域／並行アサーションのアクションを実行する領域。時点を混ぜない |
| サンプル値関数 | `$sampled`、`$past`、`$rose`、`$fell`、`$stable`、`$changed`など。現在のライブ値とサンプリング時点・履歴の値を区別する |
| 参照評価器／独立な参照モデル | 規格から結果を計算し直すPython実装／比較用に別途書いたモデル。参照評価器との一致をシミュレータoracleへ自動的に加えない |
| 2値／4値／X・Z | 0・1だけを表す値／0・1・X・Zを表す値／未知値・高インピーダンス。検査対象の型・演算・入力範囲を確認する |
| VCD（Value Change Dump）／トレース | 信号値と時刻を記録する波形形式／値や状態の時系列。通常のVCDだけでは同一時刻内のすべてのイベント領域の値を区別できない |

参照：[SVA参照評価器とフォーマル検証](sva-reference-formal-verification.md)、[参照評価器の技術資料](../tools/sva_reference/README.md)。

## 6. フォーマル検証

| 用語 | 意味・結果の範囲 |
| --- | --- |
| フォーマル検証 | 数学的なモデルについて性質を検査する方式。このスイートでは評価器から生成した検証用回路と、別に書いたRTLモデルを比較する |
| Yosys／SymbiYosys（SBY） | 検証用回路を処理するツール／ソルバー等を組み合わせてBMC・証明・到達性検査を実行する仕組み |
| BMC（Bounded Model Checking） | 指定した有限の深度まで反例を探す有界モデル検査。その先の入力長の証明にはならない |
| PDR（Property Directed Reachability） | 安全性を証明する手法。今回の系列モデルでは、固定した式・数値パラメータのもとで、入力長に上限を置かない一致を確認する |
| cover／到達性検査 | 目標とする状態や一致が起きる入力例を探す検査。1つの到達例を得たことと、すべての入力で性質が成立することを分ける |
| 反例（counterexample） | モデル間の不一致や性質への違反を起こす入力・状態の時系列。実装、参照モデル、入力の符号化などを調べる手掛かり |
| 負例／意図的な誤り（negative control／mutant） | 誤った比較モデル等を用意し、検査が反例を検出できるか確認する対照実験。予定どおりのFAILが検証経路の確認になる |
| 証明範囲／系列部分式との対応付け | 証明で固定した式・幅・初期状態・入力等の条件／実テストの部分式と検証モデルの関係。部分式の一致からアサーション全体の実行まで証明済みとは広げない |
| 証跡検査（`--check-results`） | 保存結果が現在のソース・モデル・必要な実行計画に対応するか確認する処理。ソルバーの再実行ではない |

参照：[全体ガイド](sva-reference-formal-verification.md)、[境界値の拡張と実テストとの対応](sva-formal-expansion-20261026.md)、[技術報告](../tools/sva_reference/FORMAL_REVIEW.md)。

## 7. 実行環境と証跡

| 用語 | 意味・保存する条件 |
| --- | --- |
| 固定版／開発版／commit | oracleの確認で使う特定リリース／更新される開発中の版／ソースのスナップショットを識別するID。名前が同じツールでも結果が変わり得る |
| seed（シード） | 乱数系列を選ぶ入力の一部。版・設定・テストが変われば、同じ数値だけで同じ動作を保証できない |
| DPI-C（Direct Programming Interface） | SystemVerilogとCコードを呼び合う仕組み。テストのCファイルと、ランナー・ツールの対応が必要 |
| VPI（Verilog Procedural Interface） | シミュレーションのオブジェクトやイベントをCから操作・観測するAPI。`:vpi_c:`に実行するCファイルを記録する |
| 証跡（evidence）／スナップショット | どの入力・版・設定で何を実行し、どう判定したかの記録／その実行回の結果一式 |
| SHA-256／入力ハッシュ／ランナーハッシュ | 内容を識別する値／テスト本体・期待値・関連入力の識別値／ランナー・正規化処理の識別値。ハッシュの一致自体は内容の正しさを証明しない |
| 古い証跡（stale） | 現在の入力やランナーと対応しなくなった結果。変更前の成功を、そのまま現在の実行確認へ流用しない |
| 生成テスト／生成器（generator） | `tests/gen/`に書き出すテスト／規格由来の参照モデルから入力・期待値を作るPythonコード。生成ファイルは生成器から更新する |
| lint／単体テスト／CI | ヘッダや形式等の機械検査／ツール等の個別機能の検査／設定した検査を継続実行する仕組み。何を検査する設定かと併せて結果を読む |

参照：[実行方法](../README.md#running-the-suite)、[生成テスト](../README.md#generated-tests)、[証跡の計測規則](../coverage/README.md#台帳と証跡)。
