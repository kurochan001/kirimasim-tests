# kirimasim-testsの用語集

このテストスイートのREADME、テストのヘッダ、実行結果、網羅率の資料で使う用語を、役割ごとにまとめています。運用上の疑問は[FAQ](faq.md)、全体の入口は[README](../README.md)を参照してください。

ここでいう「要求カバレッジ（テスト設計）」「実行確認率」は、このリポジトリの要求台帳と集計ルールに基づく指標です。RTLのコードカバレッジやSystemVerilogの機能カバレッジ、Nightlyのテスト一致率とは区別します。

## 1. テストの基本

| 用語 | 意味・このスイートでの使い方 |
| --- | --- |
| SystemVerilog／IEEE 1800-2023 | 検査対象のハードウェア記述・検証言語／このスイートが期待結果の根拠にする規格の版 |
| LRM（Language Reference Manual）／節・条文 | 言語規格の呼び方／動作や制約を定めた箇所。`:lrm:`に節番号を記録する |
| 規格適合性テスト（conformance test） | シミュレータの動作が言語規格に適合するかを調べるテスト。このスイートでは小さな検証用コードと期待結果を組にする |
| テスト刺激（スティミュラス）／観測点 | 検証対象に与える入力や操作／結果を確認する信号・値・メッセージ・時点。刺激を与えるだけでなく、期待結果との比較までを検証項目に含める |
| 検証項目／テストシナリオ | 仕様から導いた確認条件と期待結果／その条件を発生させる入力・操作・状態遷移の手順。1本のテストが複数の検証項目を確認する場合もある |
| 期待結果／期待出力 | 合格とする値や拒否・終了の条件／そのうち標準出力として比較する文字列。`.expected`は期待出力を保存するファイル |
| 正常系テスト／規格違反テスト | 規格上正しいコードの動作を確認するテスト／意図的に規格違反を含むコードを与え、対象の違反に対する診断と拒否を確認するテスト。規格違反テストはコンパイラの異常系テストに相当する |
| テスト実行スクリプト／ランナー（runner） | メタデータに従ってビルド・実行・出力比較を行う`tools/run_*.py`。シミュレータ用に加え、フォーマル検証用もある |
| 正規化（normalization） | 空行やツール固有の終了表示などを比較対象から除く処理。文字のある行の空白・桁・値はそのまま比較する。除去する診断やバナーはランナーごとに決めている |
| 標準出力／標準エラー／終了コード | プロセスの通常の出力先／診断などに使う出力先／プロセスの終了状態。シミュレータの診断が標準出力に出る場合もあるため、ランナーごとの比較・診断検査の対象を確認する |

参照：[テスト形式](../README.md#test-format)、[判定方法](../README.md#how-a-test-is-judged)、[テストカタログ](tests/README.md)。

## 2. メタデータと期待値の根拠

| 用語・フィールド | 意味・確認すること |
| --- | --- |
| メタデータ（metadata） | `.sv`の先頭コメントにある`:name:`などの項目。目的、規格根拠、実行方法、判定条件を記録する |
| sv-tests互換 | 他の言語テスト集でも使われるヘッダ形式に合わせていること。このスイート独自の項目もある |
| `:lrm:` | 検査する規格の節番号。節を引用していることと、その節の全要求を検査できることは分けて確認する |
| oracle（オラクル）／`:oracle:` | 期待結果の根拠／規格との照合や、期待結果を確認した固定バージョンシミュレータを記録する項目 |
| `spec`／standard only | 引用条文に基づく期待結果／`:oracle:`が`spec`だけの状態。固定バージョンシミュレータによる確認を記録していない |
| `iverilog@13.0`／`verilator@5.052` | その固定バージョンで期待結果を確認したという記録。Nightlyで使う開発版や、別のリリースへ自動で読み替えない |
| `:spec_check:` | 規格と期待結果を照合した主体。`ai`はAIによる確認、`human`は人による確認を表す |
| `:fourstate:` | 結果がX/Zに依存するか。`yes`のテストを2値の実行だけで同等に確認したとは扱わない |
| `:expected_stdout:`／`:should_fail_because:` | 期待する標準出力／規格違反のコードを拒否すべき理由。規格違反テストには期待出力ではなく診断の条件を記録する |
| `:expected_stderr_regex:`／正規表現 | 診断を照合するパターン。適切な位置と、必要に応じて意図した違反の内容を検査する。構文未対応のエラーとの区別が必要 |
| `:files:`／`:incdirs:`／`:defines:` | 追加の入力ファイル／includeの検索先／コンパイル時のマクロ。テスト本体以外の再現条件にもなる |
| `:top_module:`／`:args:` | トップとして選ぶモジュールまたはconfig／実行時の引数。各ランナーがツールに合う形式へ変換する |

参照：[メタデータ一覧](../README.md#metadata)、[期待値の決め方](../README.md#where-the-expected-outputs-come-from)。

## 3. 結果とNightly

| 用語 | 意味・読み方 |
| --- | --- |
| Match／`pass` | 出力と、指定された終了・診断の条件が期待結果に一致したテスト。正しく拒否された規格違反テストも含む |
| Differ／`fail` | テストの判定条件に合わない結果。出力差分、ビルド失敗、異常終了、規格違反のコードの受理、診断条件の不一致などを含む |
| Known difference／`known` | Icarus・Verilatorの固定バージョンoracleが付いていないテストの不一致。また、kirimasimで使える共通・専用の期待出力がなく、他ツール専用の期待出力だけがある場合。成功には数えず、ランナーが回帰失敗とする結果とも分ける |
| Unsupported／`unsupported` | ランナーが認識する未対応機能の診断や、実行できない種類のテスト。未対応は成功には数えない |
| `NOW MATCHES` | Icarusランナーの表示。oracle未登録のテストが機械的な判定では一致したという意味で、oracle認定の自動追加ではない |
| Nightlyの一致率（match rate） | 同じ実行の一致したテスト数÷結果が記録された対象テスト数。Known differenceとUnsupportedも分母に含み、未対応として実行を省略したテストも含む。固定バージョンランナーの端末の要約とは集計範囲が異なる |
| Nightly | 開発版シミュレータ等で定期実行し、履歴・比較図を公開するGitHub Actionsのワークフロー |
| Check | 固定バージョンoracleの再現、生成物、メタデータ、台帳、ツールの単体テストなどを検査するワークフロー |
| By chapter | 章ごとに各シミュレータの一致数／対象テスト数と一致率を並べる表。規格の要求ごとの網羅率ではない |
| 回帰（regression）／ratchet | 以前満たした条件が満たせなくなること／現在のNightlyでkirimasimの前回`pass`から今回`fail`への変化を失敗にする仕組み |
| `main`／`results`／suite commit | テストとツールを管理するブランチ／Nightlyの結果を公開するブランチ／その実行で使ったスイートのコミット |
| UTC／JST | 協定世界時／日本標準時。公開結果のUTC表示へ9時間を加えるとJSTになる |

参照：[Nightlyの見方](nightly-results.md)、[実行結果の形式](../tools/suite_results.py)、[ワークフロー](../README.md#workflows)。

## 4. 要求・対応付け・カバレッジ

| 用語 | 意味・計測の範囲 |
| --- | --- |
| 要求／要求ID | 規格が求める条件・動作・観測の登録単位／その識別子。1節に複数の要求があり得る |
| 要求台帳／`behaviors.json` | 要求の内容、合格基準、出典、確認に使うテストと観測点を管理する記録 |
| 出典監査（source review） | 規格の出典ブロックを調べ、要求・説明・例・参照等に分類して対応を記録すること。シミュレータでの実行確認とは別の工程 |
| 要求とテストの対応付け（トレーサビリティ） | 規格の各要求を、確認に使うテスト・刺激・観測点に結び付けること。このリポジトリでは、内容を照合してレビュー済みの対応を台帳へ登録する |
| 引用カバレッジ／条項別テスト数 | どの節をテストが引用しているか／各節に何本の直接引用テストがあるか。条件・分岐・例外の検査範囲は別途確認する |
| 要求カバレッジ（テスト設計） | テストとの対応をレビュー済みの登録要求数÷全登録要求数。検証項目の作成と要求への対応付けが完了した範囲を示す。RTL構造のカバレッジではない |
| 実行確認率 | 現在の入力・ランナーと一致するパス結果がある登録要求数÷全登録要求数。要求を単位とする指標で、テスト本数に対するパス率とは異なる。複数環境の結果を合わせた値を、単一シミュレータの規格適合率とは扱わない |
| 暫定値／確定値／分母 | 登録行に基づく集計／解釈・重複・要求単位を整理し分母を承認した集計／割合の対象となる要求集合。現在の状態は集計概要で確認する |
| 解釈保留（interpretation issue） | 規格の読み方を確定できていない登録項目。暫定値の分母に残し、解決前にテスト対応を承認しない |
| 複数テストによる検証／AND条件／`check_groups` | 1要求の条件を複数のテストで分担する対応。同じ実行回・環境で全メンバーが成功する必要がある。代替グループ間はOR |
| baseline（基準） | 要求や対応の削除・変更、複合証拠の変更などを検出するための記録。変更の根拠を確認して更新する |

参照：[集計概要](behavior-coverage-summary.md)、[計測規則](../coverage/README.md)、[要求からテストへの手順](requirements-to-tests-method.md)、[照合状況](test-requirement-matching.md)。

## 5. SVAと参照評価器

| 用語 | 意味・このスイートでの使い方 |
| --- | --- |
| SVA（SystemVerilog Assertions） | 条件や時間関係を記述する言語機能。このスイートでは、その評価・成功・失敗・アクション等の規格動作を検査する |
| 即時／コンカレントアサーション | 手続きの実行時に条件を確認する記述／サンプリングイベントに沿って時間関係を評価する記述 |
| シーケンス（sequence）／プロパティ（property） | サンプリングイベントに沿った条件の並びとマッチ区間を表すSVAの記述／シーケンスや時間演算子を使って、成立すべき条件を表すSVAの記述 |
| サンプル／tick | 特定のイベントで取り込んだ値／参照評価器でそのサンプリング時点を数える単位 |
| 前件（antecedent）・後件（consequent） | インプリケーション（含意）の条件側と、その条件が成立したときに評価する側。`a \|-> b`では`a`が前件、`b`が後件 |
| vacuous pass／vacuous success | インプリケーションで前件が成立せず、後件を評価せずにプロパティがパスすること。「むなしい成功」とも説明される。後件の動作を確認できたことにはならない |
| nonvacuous pass | インプリケーションでは、前件が成立し、後件も成立したことによるパス。vacuous passと区別して確認する |
| 空マッチ（empty match） | 長さ0のシーケンスマッチ。前件不成立によるvacuous passとは異なる |
| Preponed／NBA／Reactive | 通常のクロック付きコンカレントアサーションのサンプル値を採る領域／ノンブロッキング代入を更新する領域／コンカレントアサーションのアクションを実行する領域。時点を混ぜない |
| サンプル値関数 | `$sampled`、`$past`、`$rose`、`$fell`、`$stable`、`$changed`など。現在のライブ値とサンプリング時点・履歴の値を区別する |
| 参照評価器／独立に作成した参照モデル | 規格から結果を計算し直すPython実装／比較用に別途書いたモデル。参照評価器との一致をシミュレータoracleへ自動的に加えない |
| 2値／4値／X・Z | 0・1だけを表す値／0・1・X・Zを表す値／未知値・高インピーダンス。検査対象の型・演算・入力範囲を確認する |
| VCD（Value Change Dump）／トレース | 信号値と時刻を記録する波形形式／値や状態の時系列。通常のVCDだけでは同一時刻内のすべてのイベント領域の値を区別できない |

参照：[SVA参照評価器とフォーマル検証](sva-reference-formal-verification.md)、[参照評価器の技術資料](../tools/sva_reference/README.md)。

## 6. フォーマル検証

| 用語 | 意味・結果の範囲 |
| --- | --- |
| フォーマル検証 | 数学的なモデルについてプロパティを検査する方式。このスイートでは評価器から生成した検証用回路と、別に書いたRTLモデルを比較する |
| Yosys／SymbiYosys（SBY） | 検証用回路を処理するツール／ソルバー等を組み合わせてBMC・証明・到達性検査を実行する仕組み |
| BMC（Bounded Model Checking） | 指定した有限の深度まで反例を探す有界モデル検査。その先の入力長の証明にはならない |
| PDR（Property Directed Reachability） | 安全性を証明する手法。今回のシーケンスモデルでは、固定した式・数値パラメータのもとで、入力長に上限を置かない一致を確認する |
| cover／到達性検査 | 目標とする状態や一致が起きる入力例を探す検査。1つの到達例を得たことと、すべての入力でプロパティが成立することを分ける |
| 反例（counterexample） | モデル間の不一致やプロパティへの違反を起こす入力・状態の時系列。実装、参照モデル、入力の符号化などを調べる手掛かり |
| ネガティブコントロール／変異モデル（mutant） | 比較モデルなどに意図的な誤りを入れ、不一致を検出できることを確認する対照試験。期待どおりのFAILと反例の生成が、検証環境の検出能力を確認する結果になる |
| 証明範囲／シーケンス部分式との対応付け | 証明で固定した式・幅・初期状態・入力等の条件／実テストの部分式と検証モデルの関係。部分式の一致からアサーション全体の実行まで証明済みとは広げない |
| 証跡検査（`--check-results`） | 保存結果が現在のソース・モデル・必要な実行計画に対応するか確認する処理。ソルバーの再実行ではない |

参照：[全体ガイド](sva-reference-formal-verification.md)、[境界値の拡張と実テストとの対応](sva-formal-expansion-20261026.md)、[技術報告](../tools/sva_reference/FORMAL_REVIEW.md)。

## 7. 実行環境と証跡

| 用語 | 意味・保存する条件 |
| --- | --- |
| 固定バージョン／開発版／commit | oracleの確認で使う特定リリース／更新される開発中の版／ソースのスナップショットを識別するID。名前が同じツールでも結果が変わり得る |
| seed（シード） | 乱数系列を選ぶ入力の一部。版・設定・テストが変われば、同じ数値だけで同じ動作を保証できない |
| DPI-C（Direct Programming Interface） | SystemVerilogとCコードを呼び合う仕組み。テストのCファイルと、ランナー・ツールの対応が必要 |
| VPI（Verilog Procedural Interface） | シミュレーションのオブジェクトやイベントをCから操作・観測するAPI。`:vpi_c:`に実行するCファイルを記録する |
| 証跡（evidence）／スナップショット | どの入力・版・設定で何を実行し、どう判定したかの記録／その実行回の結果一式 |
| SHA-256／入力ハッシュ／ランナーハッシュ | 内容を識別する値／テスト本体・期待値・関連入力の識別値／ランナー・正規化処理の識別値。ハッシュの一致自体は内容の正しさを証明しない |
| 古い証跡（stale） | 現在の入力やランナーと対応しなくなった結果。変更前の成功を、そのまま現在の実行確認へ流用しない |
| 生成テスト／生成器（generator） | `tests/gen/`に書き出すテスト／規格由来の参照モデルから入力・期待値を作るPythonコード。生成ファイルは生成器から更新する |
| lint／単体テスト／CI | ヘッダや形式等の機械検査／ツール等の個別機能の検査／設定した検査を継続実行する仕組み。何を検査する設定かと併せて結果を読む |

参照：[実行方法](../README.md#running-the-suite)、[生成テスト](../README.md#generated-tests)、[証跡の計測規則](../coverage/README.md#台帳と証跡)。

用語の参考例：[PALTEKの検証環境・スティミュラスの解説](https://www.paltek.co.jp/techblog/techinfo/220125-01)、[プロパティとVacuous Successの解説](https://www.paltek.co.jp/techblog/techinfo/210816-02)、[Synopsysのフォーマル・プロパティ検証の説明](https://www.synopsys.com/ja-jp/verification/static-and-formal-verification/vc-formal.html)。

## 8. 機能間クロス検証

| 用語 | 意味・このスイートでの使い方 |
| --- | --- |
| 機能間クロス検証 | 単独では合格する機能でも、値・型・状態・時刻などの受渡しで不具合がないか確認する検証。構文が同じテストに現れるだけでは検証済みとしない |
| 因子（factor）／水準（level） | 結果に影響する検証条件／その代表値。幅、符号、状態型、格納形式、入力値などを因子にする |
| 制約を満たす行（legal row） | モデルの全因子へ水準を割り当て、仕様上の制約や代表値の選び方を満たした行。未対応のツールで動かないという理由では除外しない |
| 制約付き2因子網羅（pairwise） | 制約を満たす全体の行に現れる、すべての2因子の水準組合せを含むこと。全因子の直積を試す意味ではない |
| t-way／高次因子群（groups） | 指定したt個の因子の水準組合せを網羅する対象。2因子に加えて選んだ3因子群などを使う。全言語の網羅率や要求カバレッジとは別 |
| 必須ケース（anchors） | 他の行で同じ因子組合せを覆えても保持する、境界値や既知不具合などの確認条件 |
| 計画上の網羅／実行の充足（complete） | 選択行に対象組合せと必須ケースを含むこと／指定した実行の採用可能な成功で全対象組合せと必須ケースを確認できたこと。前者から実装の合格は推定しない |
| 故障注入／補助証跡（qualification） | 意図的に誤った処理へ置き換えて検出を確かめる方法／最小例、独立検算、確認元の選別、ビルド版などの補助記録。通常の合格数へ加算しない |
