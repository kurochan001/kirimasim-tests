# 章間クロス検証マトリクス

IEEE 1800-2023のどの章とどの章を組み合わせて検証しているかを、
縦横とも第1〜41章のCSVで確認できます。Excelなどで開けるUTF-8 BOM付きです。
左の2列は章番号と章名、上の見出しは列側の章番号です。

- [登録モデル数のマトリクス](../coverage/chapter-cross-models.csv)：各マスは、その章対に対応付けた異なるモデルの数です。
- [全選択ケースPASSのモデル数のマトリクス](../coverage/chapter-cross-passed-models.csv)：同じ配置で、後述の保存実行においてモデルの選択ケースがすべてPASSしたものだけを数えます。
- [対応と実行結果の明細](../coverage/chapter-cross-details.csv)：章対・モデルID・対応根拠・該当条件・ケース数・pass/fail/known/unsupported・代表テスト・期待値・実行結果JSONを辿れます。

0の理由と次に取り組む候補は、[0セルの仕分け](chapter-cross-triage.md)を参照してください。
分類コードを表示する別の41章×41章のCSVと、根拠・優先度・因子案・観測目標の一覧があります。
未精査のセルは対象外や低リスクと断定せず、要精査として残しています。

たとえば第7章「集合データ型」×第13章「タスクと関数」は3モデルで、
配列要素の引数渡し、添字変更後の引数の結合先、キュー要素の参照を確認しています。
第11章「演算子と式」×第12章「手続き型プログラミング文」は2モデルで、
通常のcase照合とcase insideの分岐選択を確認しています。
後者は登録2モデルに対し、全選択ケースPASSは1モデルです。

## 数字の読み方

対角線以外は**章間クロスに対応付けたモデル数**です。同じモデルが複数の章対に
対応する場合があります。対角線は**その章を主題とするモデル数**で、テストの先頭の
`:lrm:`参照に合わせています。対角線だけを合計すると全モデル数になります。
対角線は同じ章の機能を網羅的にクロスしたことを意味しません。

表は対称です。上下の三角部分や複数マスの数字を足して、テスト数やモデル総数にはしません。
`0`は「この表の集計対象に、対応付けたモデルがない」という意味です。
その章にテストが存在しない、シミュレータが未実装、要求カバレッジが0という意味ではありません。
附属書はこの表の軸に含めていません。

対象は、[有限の因子モデルとして登録したクロス検証](interaction-verification.md)だけです。
全9,335テストの集計ではありません。
[Issue #21の境界条件の回帰](p1-combination-regressions-20261030.md)のうち、
有限モデルに登録していない56件や、それ以外の通常テストは加算していません。
章全体の要求網羅率や、章どうしの全機能の直積の達成率は表していません。

## 対応付けの根拠

[対応付け台帳](../coverage/chapter-interactions.json)は、各モデルの因子・刺激・観測目的を
確認して作成したAIレビューの記録です。テストに引用されたすべての章から機械的に
章対を作る方法は採っていません。表示用の`$display`や、実行のためだけのプロセスなどを
章間クロスとして水増ししないためです。ここで挙げた章対は、確認した相互作用の整理であり、
可能な対応をすべて列挙したものではありません。

一部の条件だけがその章対を検証する場合は、台帳の`when`で因子の水準を限定します。
たとえばタスク引数モデルの第7章×第13章は、配列要素を渡すケースだけを対応付けます。
明細の「該当選択ケース数」と状態別件数はこの条件で絞った数です。
「モデル選択ケース数」はモデル全体の数なので、両者は一致しない場合があります。
代表テストは該当ケースの一例です。全選択ケースは
[クロス計画のJSON](../coverage/interaction-summary.json)の各モデルの`selection`から確認できます。

## 実行結果の扱い

生成時点では33モデル・1,585選択ケースを、対角線以外の41組の章対に対応付けています。
使用した結果は[kirimasim 55ce80b9の全33モデルの保存実行](../coverage/interaction-results/cross33-kirimasim-55ce80b9.json)で、
1,521 pass・62 unsupported・2 fail、全選択ケースPASSは29モデルです。
クロッキング入力の追加で第4/6/10/25章と第14章の章対を登録しましたが、
新モデルには未対応が残るため、この4章対の全選択ケースPASSモデル数は0です。
保存後にシミュレータを再実行したという意味ではありません。

ツールは登録済みの実行から、現在の全選択ケースを含む最新の適格なkirimasim実行を一つ選びます。
入力・期待値とランナーのハッシュ、実行中のランナー不変性を検査します。
未対応や不一致はそのまま残し、複数回の部分的な成功を合成しません。
新しい実行が一部モデルしか含まない場合は、それより前の全件を含む適格な実行を使います。
使用したJSONのパス・版・実行日時は明細の各行にも記録しています。

PASS表の判定は、章対の該当ケースだけでなく**モデルの全選択ケースが同じ実行ですべてPASS**することです。
明細の「モデル全選択ケースpass」は成立時に`1`、それ以外は`0`になります。
[クロス検証レポート](interaction-coverage.md)の因子組合せの充足判定とは異なる集計です。
Checkの成功、Nightlyの結果、規格要求のカバレッジとは分けて扱います。

## 更新と検査

モデルや選択ケースを変更した場合は、通常の生成・実行・証跡更新を先に行います。
新モデルには対応付け台帳のエントリを追加し、主題章と章対の根拠、必要な因子条件をレビューしてください。
台帳のモデル集合が計画と一致しない場合、CSVの更新は失敗します。
現在の入力に対応する全選択ケースの保存実行がない場合も失敗します。

```sh
python3 tools/interaction_coverage.py --update
python3 tools/chapter_cross_matrix.py --update
python3 tools/chapter_cross_matrix.py --check
python3 -m unittest discover -s tools -p test_chapter_cross_matrix.py
```

`--check`は台帳、入力、保存実行と3つのCSVの整合性を確認し、Checkでも実行します。
ツールはシミュレータの起動やビルドを行いません。
新しい保存実行へ切り替わった場合は、この節の件数と版も更新してください。
クロス検証の追加判断や他プロジェクトでの実践方法は
[考え方と実践手順](interaction-verification-method.md)を参照してください。
