# 機能間クロス検証の導入

全機能の直積を実行する代わりに、意味上の相互作用がある小さなモデルに分け、
制約付きの2因子網羅を基本とします。見逃したくない相互作用には3因子網羅を指定し、
幅の境界などの重要なケースを個別に保持します。生成計画と実行による確認は
[クロス検証レポート](interaction-coverage.md)で分けて集計します。

設計思想、選択アルゴリズム、モデルの追加手順、他プロジェクトやLSIへの適用方法は、
[考え方と実践手順](interaction-verification-method.md)を参照してください。
Issue #21で追加した境界条件の回帰テストと、保留した解釈・別APIの範囲は
[回帰取り込みレポート](p1-combination-regressions-20261030.md)と
[照合台帳](../coverage/combination-gaps.json)にまとめています。

## 導入済みのモデル

### スケジューリングと値の観測

`scheduling_visibility`は既存の`scheduling`生成器を利用します。
書き込み方法、読み取り方法、実行する場所、遅延を因子にし、制約を満たす325通りから
短時間実行用に51件を選びます。全因子対の126組に加え、
「書き込み方法×読み取り方法×遅延」の51組を網羅します。

各ケースの書き込みと観測時刻・イベント領域は既存生成器の参照モデルに対応します。
規格で観測結果が定まらない場合などは既存の`allowed()`で除外します。
シミュレータの未対応機能を理由にモデルの分母を減らす制約ではありません。
既存の325件と期待値は保持し、通常の全件実行でも引き続き実行します。

### ノンブロッキング代入の値と代入先の確定

`nba_capture`は次の因子を組み合わせる、新しい36件の生成テストです。

- 幅：1、32、33、64、65、129ビット。
- 状態型：2値型の`bit`、4値型の`logic`。
- 入力値：最上位・最下位ビットが立った既知値、X、Z。
- 代入先：スカラ、固定長のアンパック配列。
- 配列の添字方向：非該当、昇順`[2:3]`、降順`[3:2]`。
- 代入を実行する場所：initial、automaticタスク。
- 更新タイミング：遅延なし、代入内遅延`#1`。

スカラでは添字方向を非該当とし、配列では昇順・降順を選びます。
直積864通りのうち制約を満たす432通りを候補にし、全因子対162組と、
「幅×状態×入力値」の36組、「代入先×場所×更新タイミング」の8組を
36件で網羅します。さらに次の3件を、他のケースで因子の組合せを代替できても保持します。

- 65ビット、logic、X、降順配列、automaticタスク、遅延付きNBA。
- 129ビット、logic、Z、昇順配列、automaticタスク、遅延付きNBA。
- 129ビット、bit、X、降順配列、automaticタスク、遅延なしNBA。

NBAをスケジュールした直後に元の値と添字を変更します。代入直後、変更した刺激、
時刻1のActive領域、時刻2の結果を表示し、元の値と代入先が確定していること、
隣接要素が変わらないこと、遅延付きNBAより先にActive領域の読み取りが行われることを
期待出力で判定します。タスクを選んだケースでは、更新前にタスクが復帰しています。
代入先の寿命はstaticです。automatic変数や動的配列要素へのNBAは対象外です。

期待値はIEEE 1800-2023の10.4.2、9.4.5、4.4.2.2、4.4.2.4、6.11.2、
13.5.1、7.4.1を基にPythonで計算します。X/Zを含むケースには、bitへの変換を
確認する場合も含めて`:fourstate: yes`を付けます。テスト内に機能名が存在することだけで
クロスの充足を認定しません。

### 演算の幅・符号・代入コンテキスト

`expression_context`は、左オペランドの幅（1・32・33・64・65・129）、
右オペランドと代入先の幅（左に対し1ビット狭い・同じ・1ビット広い）、
両オペランドそれぞれの符号属性、加算・減算・乗算をクロスします。
幅0になる組合せを除いた588通りから51件を選びます。
全因子対143組に加え、「幅×代入先の幅×演算子」の51組と
「左の符号×右の符号×演算子」の12組を網羅します。

1件ごとに4組の入力を与え、負値、最上位ビット、桁上がり、切り捨てを確認します。
期待値は11.6.1・11.8.1・11.8.2に基づき、演算前に代入先の幅も含めて
評価幅を決め、両オペランドがsignedのときだけ符号拡張します。
129ビットの符号付き乗算、65ビット付近の混合符号の加算、33ビット付近の減算を
必須ケースにします。除算、シフト、自己決定式によるコンテキストの遮断は今回のモデルに含みません。

### パック配列の添字方向と部分選択への書き込み

`packed_part_select`は、幅（1・32・33・64・65・129）、添字の昇順・降順、
インデックス付き部分選択の`+:`・`-:`、選択幅（1ビット・全体の半分）、
選択位置（下位端・上位端・内部）、bit/logic、既知値/X/Zをクロスします。
幅0の選択と、端・内部が同じ位置になる組合せを除いた744通りから36件を選びます。
全因子対162組と、「幅×状態×入力値」の36組、
「添字方向×選択方向×選択位置」の12組を網羅します。

添字の下限を4にして、0始まりを仮定した実装も検出対象にします。
実行時のベース添字と定数の選択幅で読み書きし、書き込み前後の全ビットと
選択範囲を表示します。既知値は元の選択範囲の反転値とし、書き込みが必ず変化を
起こすようにします。選択していないビットの保持も期待値で確認します。
期待値は11.5.1・7.4.1・6.11.2に基づき、添字の構文とは独立した
ビットの重み順で計算します。範囲外アクセスは今回の対象外です。
65ビットの昇順`-:`によるZ書き込み、129ビットの内部へのX書き込み、
33ビットの上位端でのXからbitへの変換を必須ケースにします。

### 条件演算子のX/Z結合と代入先への変換

`conditional_merge`は、幅（1・33・65・129）、両分岐それぞれの符号属性、
条件（0・1・X・Z）、分岐値のパターン（同一既知値・反転既知値・同一X/Z・異なるX/Z）、
代入先の幅（1ビット狭い・同じ・1ビット広い）、bit/logicをクロスします。
幅0になる組合せを除いた1,408通りから32件を選びます。
全因子対185組と、「幅×条件×状態」の32組、
「条件×分岐パターン×状態」の32組、「左分岐の符号×右分岐の符号×代入先の幅」の12組を網羅します。

期待値は11.4.11・11.6.1・11.8.1・11.8.2・6.11.2に基づきます。
条件が既知なら片方を選び、X/Zなら拡張した両分岐を表11-20でビットごとに結合し、
最後に切り捨てとbitへの変換を適用します。同じ位置のZ/Zも、曖昧な条件ではXになります。
129ビットの同一X/Z分岐の結合、65ビットの混合符号の拡張、
33ビットからの切り捨てと2値変換を必須ケースにします。
両分岐の元の幅は同一とし、非整数型や副作用を持つ分岐式は対象外です。

相対許容差は`a`の`b`パーセントを0方向へ切り捨てた値で両端を作り、必要なら両端を入れ替えます。
符号付きの負の`b`や負の`a`で入れ替えが起き、相対許容差では切り捨てが結果に効く値を選んでいます。

各行は4組の入力を使います。比較時の型で拡張した端点（一致すべき値）、端点自身の符号で
拡張した端点（誤って符号拡張する実装だけが一致する値）、端点の1つ下、全1などを、
左辺の幅で与えます。入力、与えた端点と格納後の端点、1ビットの判定結果、
広いlogic/bitへの直接代入結果と`$bits`を観測します。コロンで書く範囲では、
同じ端点を関係演算子で書いた判定も並べて出力します。混在する集合では、
X/Zを持つ端点と同じ変数を値としても並べ、全1の値を加えます。範囲ではX/Zが比較をXにし、
値ではワイルドカードになる違いと、一致がXに優先するORを確認します。

規格本文が一つの結果を定めない組合せは、制約と入力の選び方で避けています。

- 逆順の範囲は、符号の解釈によらず左端が大きい正の値（3と1）で作ります。
  幅1では作れないため除き、X/Zを含む空の範囲の扱いは本文が定めないので既知値だけにします。
- 閉区間の端点にX/Zがある場合は、もう一方の端点を満たす入力だけを使います。
  二つの関係を`&&`で結ぶ読み方でも、一方の比較がXなら範囲をXとする読み方でも、結果はXになります。
- 許容差は`a`の型の範囲を超えない値に限ります。端点の計算を広いコンテキストで行うか、
  `a`の型で行うかによって結果が変わらないようにするためです。

33ビットsigned閉区間と広いunsigned左辺、129ビットbitの絶対許容差と広いunsigned左辺、
65ビットsignedの相対許容差と狭い左辺、64ビットunsigned端点Xと値の混在、
32ビットの逆順の範囲と値の混在、1ビットsigned`[$:hi]`と左辺Xを、6件の必須条件として保持します。

独立検算は、ビット列ではなく整数の区間で各ケースを計算し直します。許容差は10進の厳密計算を
0方向へ切り捨てます。参照モデルへの故障注入では、端点を自身の符号で拡張する、端点のX/Zを
0と読む、許容差の両端を入れ替えない、相対許容差を四捨五入する、`$`を端点の型から取る、
逆順の範囲の両端を入れ替える、左辺のX/Zを0と読む、の7種類すべてを2件以上のケースで検出しました。

非整数、異なる型の集合要素、副作用付き式、評価順は対象外です。

### case insideの項目の種類と選択

`case_inside_selection@1`は、項目の幅（1・32・33・64・65・129）、ケース式の幅
（1ビット狭い・同じ・1ビット広い）、ケース式と項目のsigned/unsigned、項目のbit/logic、
先頭項目の種類（値・範囲`[lo:hi]`・2要素の固定配列・2つの値のリスト）、入力（既知値・
ケース式X・項目X・項目Z）、修飾子（なし・`unique0`）、3番目の項目（変数・評価回数を数える
関数呼び出し）をクロスします。8,704通りから34件を選び、全因子対315組に加え、
次の3因子群の154組を網羅します。

- 項目の幅×ケース式の幅の関係×ケース式の符号
- ケース式の符号×項目の符号×先頭項目の種類
- 項目の状態型×入力×先頭項目の種類
- 先頭項目の種類×入力×修飾子
- ケース式の幅の関係×項目の符号×先頭項目の種類
- 3番目の項目×修飾子×先頭項目の種類

12.5.4に従い、ケース式を左辺、各項目を右辺として`inside`で比較します。値の項目のX/Zは
ワイルドカード、範囲の端点のX/Zは比較をXにし、ケース式のX/Zはワイルドカードになりません。
結果が1の項目だけが一致で、0とXはどちらも不一致として次の項目へ進み、どれも一致しなければ
`default`を実行します。全項目は同じ型・幅にし、整数リテラルの項目は使いません。
このため、各比較の幅と符号は11.8.1・11.8.2のケース式と項目の型の組で決まり、
12.5の全項目をそろえる規則とも同じ結果になります。

各`case`は、先頭項目、値の`second`、変数または関数呼び出しの3番目、`default`の順です。
4組のケース式で先頭・2番目・3番目・`default`をそれぞれ狙い、狙いに届く値のうち、
手前の項目がXになる値を優先します。値の候補には、比較時の型で拡張した項目値と、
項目自身の符号で拡張した項目値（誤って符号拡張する実装だけが選ぶ値）を含めます。
ケース式は呼出し回数を数える関数で与え、毎回1回だけ評価されることを観測します。
修飾子なしでは、手前の項目が一致すると3番目の関数は呼ばれません。
`unique0`では一致した後も残りの項目を評価するので呼ばれたこと（12.5.3）を出力し、
一致する項目が2つ以上になる入力は使いません。格納前後の項目値も出力します。

priority・uniqueは、一致がないときの違反報告と`default`の関係を本文が明記しないため対象外です。
3番目の項目を変数と関数呼び出しの因子に分けたのは、副作用のある項目が未対応の実装でも、
幅・符号・X/Zと項目の種類の相互作用を確認できるようにするためです。

33ビットsigned固定配列と広いunsignedのケース式、65ビットsigned範囲と`unique0`・関数呼び出し、
129ビットの値の項目X、64ビットbitのリストの項目Zと`unique0`、32ビットのケース式Xと
関数呼び出し、1ビットsigned範囲の項目X、64ビットunsigned範囲の端点Xで先頭がXになり
2番目が選ばれるケースを、7件の必須条件として保持します。

独立検算は、整数の比較と線形探索で各ケースを計算し直します。参照モデルへの故障注入では、
Xの結果を一致とみなす、項目を自身の符号で拡張する、ワイルドカード比較の左右を入れ替える、
最後に一致した項目を選ぶ、項目のX/Zを0と読む、一致の後も3番目を呼ぶ、
比較ごとにケース式を評価し直す、の7種類すべてを検出しました。

項目内の複数の式の評価回数、副作用の順序、casez/casexとの組合せ、非整数の項目は対象外です。

## 計画と実行証跡の扱い

`generators/interaction_cover.py`は制約を満たす完全な組合せを列挙し、そこに含まれる因子対・因子群から分母を作ります。
部分的な割当てだけでは、他の制約と両立できるかを判定しません。
選択は決定的な貪欲選択と冗長ケースの除去によるもので、最小件数の一般的な保証はありません。
直積が10,000行を超えるモデルは拒否します。対象を意味ごとに分割してから登録します。

`tools/interaction_coverage.py`は、生成ファイルと期待値の一致を確認し、実行証跡の
シミュレータ版、日時、ランナーのハッシュ、各テストの入力ハッシュを検査します。
実行中にランナーや入力が変わった結果も合格に含めません。

- `pass`：現行の入力・ランナーと一致した合格。合格確認済みの組合せに算入します。
- `fail`、`known`、`unsupported`：合格として利用しません。
- `stale`：入力ハッシュが異なるなど、現行の証跡として利用できない結果です。
- `not_run`：その実行に結果がありません。

版やseedが異なる実行の部分成功は合成しません。必須ケースはそのケース自体の合格が
必要です。失敗した実行でどの刺激に到達したかという、生の到達率は計測していません。
この集計の100%は登録モデルの対象組合せについての値であり、全言語の組合せ網羅や
不具合がないことを示す値ではありません。

### イベントORと項ごとのiff条件

`event_or_iff@1`は、既存の`edge_event_expression`が対象外としていたイベントORと
`iff`の相互作用を独立したモデルにしたものです。
[生成器](../generators/interaction_iff.py)は9.4.2.1・9.4.2.3・12.4・15.5.1を根拠に、
次の6因子を組み合わせます。

`default_argument_scope`は、第13章のデフォルト引数の評価に、第23章の階層呼出しと、

### モデル変更時の更新

モデルやテストを変えたときは、必要なケースを再実行して新しい証跡を保存してください。
古い結果の入力ハッシュだけを書き換えて合格を引き継いではいけません。

```sh
python3 generators/generate.py
# シミュレータで実行し、必要ならcoverage/interaction-results/へ新しいJSONを保存
python3 tools/interaction_coverage.py --update
python3 tools/interaction_coverage.py --check
python3 tools/chapter_cross_matrix.py --update
python3 tools/chapter_cross_matrix.py --check
python3 tools/chapter_cross_triage.py --update
python3 tools/chapter_cross_triage.py --check
python3 -m unittest discover -s tools -p test_interaction_coverage.py
```

生成テスト追加時はREADMEの統計、カタログ、条項別テスト数、要求照合一覧、要求カバレッジの
生成物も通常どおり更新します。新しいクロスモデルは要求台帳の分母を変更しません。
章間の対応は[章間クロス検証マトリクス](chapter-cross-matrix.md)の台帳にも登録し、CSVを更新します。
[0セルの仕分け](chapter-cross-triage.md)に該当章対の既存検証や候補がある場合は、登録後の扱いを再確認します。
新規テストを要求カバレッジに算入するには、別途、刺激・観測・期待値と要求の対応を
レビューして登録する必要があります。既存テスト、負例、期待値は維持します。

方式の背景は[NIST SP 800-142, Practical Combinatorial Testing](https://csrc.nist.gov/pubs/sp/800/142/final)
を参照してください。ここでは2因子だけで十分とは仮定せず、指定した3因子群と
必須ケースを併用します。
