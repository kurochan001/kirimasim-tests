# FST tests for the kirimasim waveform backend (2026-10-29)

FST is the GTKWave/libfst waveform format. It is **not** a format of
IEEE 1800-2023: §21.7.1 lets `$dumpfile` name the file but leaves the format to
the implementation. These tests are therefore prepared for
kirimasim's planned FST backend, and `:oracle:` is `spec` alone. Icarus and
Verilator report them as known differences because their builds in this suite
write VCD, not FST.

References:

- kirimasim, [`docs/spec/WAVEFORM.md`](https://github.com/kurochan001/kirimasim/blob/main/docs/spec/WAVEFORM.md)
- kirimasim, [`docs/notes/fst-dependency-setup.md`](https://github.com/kurochan001/kirimasim/blob/main/docs/notes/fst-dependency-setup.md)
- libfst `fstapi.c` / `fstapi.h` (the header layout below)

## Tests

### `tests/ch21/test_fst_header_and_dumpfile.sv`

`$dumpfile("wave.fst")`, `$dumpvars(0, ...)`, one value change, `$dumpflush`,
then the test reads the first 74 bytes of the file and prints:

```text
bytes=74 tag=0 len=329 timescale=-9
```

- `tag=0` is libfst's `FST_BL_HDR`.
- `len=329` is the FST header section length, written big-endian.
- `timescale=-9` is the byte at offset 73 for 1 ns (`-9` as a signed byte).
- A VCD writer starts with `$date`, so this also distinguishes FST from VCD
  written under an `.fst` name.

### `tests/ch21/test_fst_dump_control_keeps_header.sv`

The same header check after `$dumpoff`, `$dumpon` and `$dumpall`. It checks the
control tasks do not turn the stream into a VCD file or corrupt the FST header:

```text
bytes=9 tag=0 len=329
```

## Running them

With a kirimasim build that has the FST backend:

```sh
python3 tools/run_kirimasim.py tests/ch21/test_fst_header_and_dumpfile.sv \
  tests/ch21/test_fst_dump_control_keeps_header.sv
```

Today Icarus Verilog 13.0/14.0 and Verilator 5.052 mark both as `known`: they
either write VCD under the `.fst` name or do not implement the dump control
needed here. That is expected and does not fail the Check workflow.

## Limits and next tests

These two tests check the file type and header only. They do **not** yet check
the FST hierarchy, variable declarations, value changes, time steps or the
effect of `$dumpoff`/`$dumpon` on the recorded data. The libfst reader and runner
described below provide the harness for further checks; no suite test currently
has `:fst_expected:`. The next batch should cover:

1. one module and one child scope: `$scope`/`$var` hierarchy and variable
   count;
2. 1-bit, 4-state, multi-bit and real values at several times;
3. `$dumpoff`, `$dumpon`, `$dumpall`, `$dumpflush`, `$dumplimit` and
   `$dumpfile` timing;
4. a comparison of the FST stream with the VCD stream for the same design,
   after normalizing the format-specific header.

Derive those expected values from the intended waveform behavior and the FST
format, then check them with an external reader. A reader validates the file;
it does not by itself qualify an `iverilog@13.0` or `verilator@5.052` oracle.
Those tokens still require the corresponding fixed-release simulator run.

## libfst reader harness

The harness is in `tools/` and does not vendor libfst. It uses a libfst source
tree supplied by the developer, for example from the kirimasim build:

```sh
LIBFST_SRC="$HOME/Projects/kirimasim/build/release/_deps/libfst-src"
```

`tools/fst_read.c` is a small reader that prints a deterministic text view:

```text
start=0
end=10
scopes=1
vars=2
timescale=-9
scope 0 top
var 16 2 8 a
var 5 2 1 b
t=0 a=00000101
t=0 b=0
t=10 a=10100101
t=10 b=1
```

Build and run it through `tools/fst_reader.py`. This needs a C compiler and
the zlib and bzip2 development libraries. The committed fixture provides a
reader check without a simulator:

```sh
python3 tools/fst_reader.py tools/fixtures/fst/simple.fst 0 10 \
  --libfst-src "$LIBFST_SRC"
```

`tools/run_fst.py` is the runner for semantic FST tests. A test opts in with
these fields in its metadata comment. `:fst_file:` is optional (default
`wave.fst`); `:fst_times:` is optional (default start and end times):

```text
:fst_file: wave.fst
:fst_times: 0 10 20
:fst_expected: @test.fst.expected
```

It runs the simulator in a temporary directory, reads the FST file with
`tools/fst_reader.py`, and compares the text with `:fst_expected:`. It also
checks `:expected_stdout:` with the normal normalizer. The source shapes are
the same as `run_kirimasim.py`. The following is a template for a future test;
`test_some_fst_test.sv` is not included in the suite:

```sh
python3 tools/run_fst.py --simulator /path/to/kirimasim \
  --libfst-src "$LIBFST_SRC" tests/ch21/test_some_fst_test.sv
```

`tools/fixtures/fst/simple.fst` is a 505-byte fixture generated by
`tools/fst_fixture.c`; `tools/test_fst_reader.py` and
`tools/test_fst_runner.py` use it to check the reader and the runner without a
simulator. Both test modules skip when no libfst source is found through
`LIBFST_SRC` or the reader's development paths, so the Check
workflow does not need libfst.
