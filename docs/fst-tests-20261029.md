# FST tests for the kirimasim waveform backend (2026-10-29)

FST is the GTKWave/libfst waveform format. It is **not** a format of
IEEE 1800-2023: §21.7.1 lets `$dumpfile` name the file but leaves the format to
the implementation. These tests are therefore prepared for
kirimasim's planned FST backend, and `:oracle:` is `spec` alone. Icarus
Verilator report them as known differences because their builds in this suite
write VCD, not FST.

References:

- kirimasim, [`docs/spec/WAVEFORM.md`](https://github.com/kurochan001/kirimasim/blob/main/docs/spec/WAVEFORM.md)
- kirimasim, [`docs/notes/fst-dependency-setup.md`](https://github.com/kurochan001/kirimasim/blob/main/docs/notes/fst-dependency-setup.md)
- libfst `fstapi.c` / `fstapi.h` (the header layout below)

## Tests

### `tests/ch21/test_fst_header_and_dumpfile.sv`

`$dumpfile("wave.fst")`, `$dumpvars(0, ...)`, one value change, `$dumpflush`,
then the test reads the first 74 bytes of the file and prints:

```text
bytes=74 tag=0 len=329 timescale=-9
```

- `tag=0` is libfst's `FST_BL_HDR`.
- `len=329` is the FST header section length, written big-endian.
- `timescale=-9` is the byte at offset 73 for 1 ns (`-9` as a signed byte).
- A VCD writer starts with `$date`, so this also distinguishes FST from VCD
  written under an `.fst` name.

### `tests/ch21/test_fst_dump_control_keeps_header.sv`

The same header check after `$dumpoff`, `$dumpon` and `$dumpall`. It checks the
control tasks do not turn the stream into a VCD file or corrupt the FST header:

```text
bytes=9 tag=0 len=329
```

## Running them

With a kirimasim build that has the FST backend:

```sh
python3 tools/run_kirimasim.py tests/ch21/test_fst_header_and_dumpfile.sv \
  tests/ch21/test_fst_dump_control_keeps_header.sv
```

Today Icarus Verilog 13.0/14.0 and Verilator 5.052 mark both as `known`: they
either write VCD under the `.fst` name or do not implement the dump control
needed here. That is expected and does not fail the Check workflow.

## Limits and next tests

These two tests check the file type and header only. They do **not** yet check
the FST hierarchy, variable declarations, value changes, time steps or the
effect of `$dumpoff`/`$dumpon` on the recorded data. A full check needs a reader
(such as libfst's reader or `fst2vcd`) and a normalization step for scope and
variable ordering. The next batch should cover:

1. one module and one child scope: `$scope`/`$var` hierarchy and variable
   count;
2. 1-bit, 4-state, multi-bit and real values at several times;
3. `$dumpoff`, `$dumpon`, `$dumpall`, `$dumpflush`, `$dumplimit` and
   `$dumpfile` timing;
4. a comparison of the FST stream with the VCD stream for the same design,
   after normalizing the format-specific header.

Those tests should stay `:oracle: spec` until a fixed external FST reader is
part of the suite; otherwise the expected values would depend on the simulator
under test.
