# kirimasim波形バックエンド（2026-10-29）に対するFSTテスト

[English](fst-tests-20261029.md) / [日本語](fst-tests-20261029.ja.md)

FSTはGTKWave／libfstの波形形式である。これはIEEE 1800-2023が定める形式ではない。§21.7.1は、`$dumpfile`によるファイル名の指定を認めるが、形式は実装に委ねている。したがって、これらのテストはkirimasimで計画中のFSTバックエンドに向けて準備したもので、`:oracle:`は`spec`だけである。IcarusとVerilatorでは、このスイートのビルドがFSTではなくVCDを出力するため、既知の差異として報告します。

参考文献:

- kirimasim, [`docs/spec/WAVEFORM.md`](https://github.com/kurochan001/kirimasim/blob/main/docs/spec/WAVEFORM.md)
- kirimasim, [`docs/notes/fst-dependency-setup.md`](https://github.com/kurochan001/kirimasim/blob/main/docs/notes/fst-dependency-setup.md)
- libfst `fstapi.c` / `fstapi.h` (下のヘッダレイアウト)

<a id="tests"></a>

## テスト

### `tests/ch21/test_fst_header_and_dumpfile.sv`

`$dumpfile("wave.fst")`、`$dumpvars(0, ...)`、1回の値変化、`$dumpflush`の順に実行した後、ファイルの先頭74バイトを読み出して次を表示します。

```text
bytes=74 tag=0 len=329 timescale=-9
```

- `tag=0` は libfst の `FST_BL_HDR` である。
- `len=329`はFSTヘッダセクションの長さであり、ビッグエンディアンで表されます。
- `timescale=-9`は、オフセット73にあるbyteで、1 ns続きます（符号付きbyteとしての`-9`）。
- VCDの書込み側は`$date`で始まるため、`.fst`の名前で書き込まれたVCDとFSTを区別することもできる。

### `tests/ch21/test_fst_dump_control_keeps_header.sv`

`$dumpoff` , `$dumpon`分と`$dumpall`分に同じヘッダーチェック制御タスクがストリームをVCDファイルに変えず、FSTヘッダも破損しないことを検査する。

```text
bytes=9 tag=0 len=329
```

<a id="running-them"></a>

## 実行方法

FSTバックエンドを持つkirimasimビルドの場合：

```sh
python3 tools/run_kirimasim.py tests/ch21/test_fst_header_and_dumpfile.sv \
  tests/ch21/test_fst_dump_control_keeps_header.sv
```

現在、Icarus Verilog 13.0/14.0とVerilator 5.052は、どちらのテストも`known`とする。`.fst`の名前でVCDを書き込むか、ここで必要なダンプ制御を実装していないためである。これは想定どおりであり、Checkワークフローを失敗させない。

<a id="limits-and-next-tests"></a>

## 限界と次のテスト

これらのテストはファイルタイプとヘッダのみをチェックします。現時点では、FSTの階層、変数宣言、値の変化、時間ステップ、`$dumpoff`/`$dumpon`が記録データへ及ぼす効果は確認していません。次に述べるlibfstリーダとランナは、さらなるチェックのためのハーネスを提供します。`:fst_expected:` を持つスイートテストはありません。次のバッチは次の内容を含むべきです：

1. 1つのモジュールと1つの子スコープ: `$scope` / `$var` 階層と変数数;
2. 1-bit、4状態、multi-bit、実数の値を複数の時刻で確認します。
3. `$dumpoff`、`$dumpon`、`$dumpall`、`$dumpflush`、`$dumplimit`、`$dumpfile`のタイミング。
4. 形式固有のヘッダを正規化した後、同じ設計のFSTストリームとVCDストリームを比較する。

意図した波形の動作とFST形式から期待値を導き、外部の読取りツールで確認する。読取り側でファイルの妥当性を検証する。これだけでは、`iverilog@13.0`または`verilator@5.052`のオラクルとしては認定しない。これらのトークンは，対応する固定リリースシミュレータの実行を必要とする。

<a id="libfst-reader-harness"></a>

## libfst リーダーハーネス

ハーネスは`tools/`にあり、libfstを同梱していない。開発者が提供した libfst ソースツリーを使用します。例えば、kirimasim のビルドから:

```sh
LIBFST_SRC="$HOME/Projects/kirimasim/build/release/_deps/libfst-src"
```

`tools/fst_read.c` は決定論的なテキストビューを出力する小さなリーダです。

```text
start=0
end=10
scopes=1
vars=2
timescale=-9
scope 0 top
var 16 2 8 a
var 5 2 1 b
t=0 a=00000101
t=0 b=0
t=10 a=10100101
t=10 b=1
```

`tools/fst_reader.py`を通じてビルド・実行する。Cコンパイラと、zlibおよびbzip2の開発用ライブラリが必要である。これは、シミュレータを使用せずに読み取りチェックを行うためのコミットされたフィクチャです。

```sh
python3 tools/fst_reader.py tools/fixtures/fst/simple.fst 0 10 \
  --libfst-src "$LIBFST_SRC"
```

`tools/run_fst.py`は、FSTの意味を検査するテストのランナーである。テストのメタデータコメントにこれらのフィールドを記載することで、この検査を有効にする。`:fst_file:`は省略可能（既定値は`wave.fst`）。`:fst_times:` はオプション (デフォルトの開始と終了時刻):

```text
:fst_file: wave.fst
:fst_times: 0 10 20
:fst_expected: @test.fst.expected
```

一時ディレクトリでシミュレータを実行し、`tools/fst_reader.py`でFSTファイルを読み、得られたテキストを`:fst_expected:`と比較します。通常の正規化処理を使い、`:expected_stdout:`も検査する。シミュレータの終了コードは0、または`:expected_exit:`の指定どおりでなければならない。`--json`は、ほかのランナーと同じく入力とランナーのフィンガープリントを記録する。ソースの構造は`run_kirimasim.py`と同じである。以下は将来のテストのテンプレートである。`test_some_fst_test.sv` はスイートに含まれていません:

```sh
python3 tools/run_fst.py --simulator /path/to/kirimasim \
  --libfst-src "$LIBFST_SRC" tests/ch21/test_some_fst_test.sv
```

`tools/fixtures/fst/simple.fst`は、`tools/fst_fixture.c`で生成した505-byteのフィクスチャである。`tools/test_fst_reader.py`と `tools/test_fst_runner.py`は，シミュレータなしで読み手とランナをチェックするために使用する。どちらのテストモジュールも、`LIBFST_SRC`または読取り側の開発用パスからlibfstソースが見つからない場合はスキップするため、Checkワークフローはlibfstを必要としない。
