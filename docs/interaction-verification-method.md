# 機能間クロス検証の考え方と実践手順

この資料は、本リポジトリで機能間クロス検証を導入した際の判断、設計方法、
実装・計測の手順をまとめたものです。新しい項目を追加する担当者と、
別のソフトウェアやLSIのロジック検証へ適用する担当者が再利用できるようにしています。

導入済みモデルの詳細と実行結果は[検証ガイド](interaction-verification.md)、
現在の因子・分母・実行ごとの達成状況は[クロス検証レポート](interaction-coverage.md)、
規格要求とテストの対応付けは[要求からテストを作る手順](requirements-to-tests-method.md)を
参照してください。本資料は方法を説明し、最新の件数はレポートで確認します。
有限モデルとは別に追加する境界条件の回帰テストは、
[Issue #21の回帰取り込みレポート](p1-combination-regressions-20261030.md)と
[照合台帳](../coverage/combination-gaps.json)で、既存テストの再利用、規格根拠、保留事項を管理します。

## 1. 設計思想

### 単独機能の合格だけでは分からない境界を検証する

一つずつ正しく動く機能でも、値・状態・型・タイミングを受け渡す境界で不具合が生じます。
例えば、符号付き演算そのものと幅変換そのものが合格していても、
「代入先の幅に広げてから除算する」処理が正しいとは限りません。
NBAも、最終値だけでは値と代入先をいつ確定したかが分かりません。

そこで、機能名を並べることより、**何と何が相互作用し、どの観測で正誤を区別するか**を
先に決めました。モデルの一行には、刺激、観測点、規格から決めた期待値を対応付けます。
テスト内に二つの構文が現れるだけでは、そのクロスを検証したとは扱いません。

### 小さな意味単位へ分けてから組合せを選ぶ

全機能の直積は作りません。「演算のコンテキスト」「NBAの値と代入先の確定」
「配列のサイズ変更」など、結果を説明できる単位に分けます。その中で、
制約付きの2因子網羅を基本とし、故障の起こり方に直結する因子群は3因子以上で網羅します。
境界値と既知不具合の再現条件は、組合せが他のケースで代替されても必須ケースとして残します。

この方法は、選んだ低次の相互作用を少ないケースで確認するための設計です。
2因子網羅によって、任意の高次の不具合を検出できるという保証はありません。
モデルに含めていない値・状態・順序にも保証は及びません。

### 期待値と分母を実装の都合に合わせない

期待値はIEEE 1800-2023に基づき、検証対象の実装から独立したPythonモデルで計算します。
シミュレータの出力を期待値に写しません。
他のシミュレータとの照合は期待値の確認に使います。食い違った場合は仕様解釈とテストを
再確認し、未対応や不一致も残します。合格率を上げるために対象を除外しません。

既存テストは保持します。短時間実行用の選択を追加することと、通常の回帰テストを
削減することは別です。また、クロスの達成数をそのまま全規格の要求カバレッジへ加算しません。

## 2. 何をモデル化するか

### 追加候補の優先順位

既存テストと仕様を調べ、次の観点で追加する項目を選びます。

- 同じ値や状態を複数の機能が読み書きする。
- 型変換、幅変換、バッファ、階層、引数などの境界を通過する。
- 優先順位、遅延、同時実行、更新前後の違いが結果に影響する。
- 1・32・33・64・65・129ビットなど、実装上の境界をまたぐ。
- X/Z、空、満杯、ゼロ、負数など、通常値と処理が変わる。
- 既知不具合がある、または既存モデルで明示的に対象外としている。

既存テストが同じ刺激と観測を持つ場合は、再利用を先に検討します。
最初の`scheduling_visibility`は既存の325件を保持し、その中から51件を選ぶ方式でした。
新しい刺激が必要な項目では、生成器と独立した期待値を追加しています。

候補すべてを因子モデルへ変換する必要はありません。Issue #21では、イベント、NBA、
複合型、I/Oの境界条件を確認する56件と、ファイル監視の有限モデルから選んだ18件を追加しました。
前者は具体的な境界条件の回帰テストとして台帳へ対応付けます。
後者は登録元の記述位置×キュー/動的配列×MCD/FDの36通りを定義し、
全因子対40組と必須ケース3件を保つ18件を選びます。
因子と対象組合せを定義していない回帰テストの件数を、t-wayの達成数へ加えません。

### 因子と水準は、結果に影響する違いから決める

因子は幅、符号、格納先の状態型、操作、入力値、時刻などです。
水準はその代表値です。「幅を広げる」のような相対値は、どの幅を基準にするかも定義します。
例えば`state=bit`が入力型を表すのか、最終代入先だけを表すのかで期待値は変わります。

水準を増やす前に、その差を観測できる刺激を用意します。1ビット要素の配列では
一回の0/1パターンだけで複数の位置を区別できないため、入力を巡回させた二回の観測を使いました。
除算のX/Zケースには既知入力も与え、一律Xになる結果だけで符号や幅のクロスを認定することを
避けました。一行が一つの入力ベクトルに限定されるわけではありません。

副作用のある式では、値だけでなく評価回数も観測します。複合シフト代入の40件では、
配列要素や部分選択の添字関数が次の戻り値を変更するようにし、呼出し回数・書込み先・
非選択領域を同時に確認します。規格上1回の評価を2回にする故障注入でも検出を確認しました。
Verilatorで観測した2回評価を期待値へ取り込まず、差異として保存しています。

### 組合せの制約とツールの未対応を区別する

制約は仕様上成立しない条件と、意味が同じ代表値の重複を除くために使います。
幅1から1ビット狭める幅0や、容量2に対する初期サイズ3などが例です。
空配列で入力値が存在しない場合は、値因子を一つの水準へ固定しました。
除外の理由は生成器とレポートへ記録します。

現在の実装が処理できない、期待値が一致しない、生成が難しいという理由で組合せを除外しません。
仕様違反の入力を拒否する検査は、正常な組合せモデルと区別して設計します。

対象の分母は、**残りの因子を補えば制約を満たす完全な組合せになるもの**から求めます。
因子ごとの水準を機械的に掛けたペア集合を分母にすると、実現不能な組まで不足に数えてしまいます。

## 3. 少ないケースを選ぶ仕組み

[interaction_cover.py](../generators/interaction_cover.py)の`Model`は、次の順で選びます。

1. 全因子の直積を列挙し、`legal`で制約を満たす行を残す。
2. 制約を満たす行から全因子対と指定した高次因子群を取り出し、対象の組合せ集合を作る。
3. `anchors`で指定した必須ケースを先に選ぶ。
4. 未充足の組合せを最も多く埋める行を順に加える。
5. 他の選択行で全対象を満たせる冗長な行を除く。ただし必須ケースは除かない。

因子と水準の順序を固定すれば選択は再現できます。貪欲選択と冗長除去であり、
最小件数の解を保証するアルゴリズムではありません。
現在の実装の列挙上限は、**制約を適用する前の全直積で既定10,000行**です。
超える場合は意味単位や構成を分けます。この値は検証対象の仕様上の制限ではありません。

`groups`には、共有状態・変換順序・優先順位などで同時に効く因子群を指定します。
例えば「幅×状態型×X/Z」「容量×初期サイズ×操作」です。モデルの因子全体を
無条件に高次クロスへ戻すのではなく、リスクと仕様上の根拠から選びます。
3因子で足りない相互作用には、さらに高次の群や明示的な必須シナリオを使います。

選択器だけを試す最小例です。これは実行可能なテストベンチの生成までは行いません。

```python
import sys
sys.path.insert(0, "generators")
from interaction_cover import Model

model = Model(
    "example_word_update",
    (("width", ("1", "32", "33", "64", "65", "129")),
     ("state", ("bit", "logic")),
     ("update", ("blocking", "nba")),
     ("value", ("known", "x", "z"))),
    legal=lambda row: True,
    groups=(("width", "state", "value"),),
    anchors=(("129", "logic", "nba", "z"),),
)
selected = model.select()
assert set(model.anchors) <= set(selected)
assert {t for row in selected for t in model.targets(row)} == set(model.universe())
print(len(model.rows()), len(selected))
```

## 4. 一行を、正誤が分かるテストへ変換する

入力、途中の値、最終値を分け、どの段階で誤りが起きたかを判別できるようにします。
隣接要素や非選択ビットの保持、コピー元を変更した後の独立性も必要に応じて観測します。
イベント領域や遅延が関係する場合は、観測時刻と競合の有無を仕様で説明します。
規格が実行順序を定めない競合に、一意の期待値を置いてはいけません。

期待値の計算は、検証対象とは異なる表現で行います。例えば、
ビット列の重み順による部分選択、任意精度整数による演算、配列リストによるコピーを使います。
商・剰余ではPythonとSystemVerilogの負数の丸めの差を明示的に扱いました。
仕様に基づく参照モデルにも誤りはあり得るため、別担当のレビューと別計算法による検算を行います。
本導入で使った独立レビューはAIによるもので、人による承認を意味しません。

参照モデルのユニットテストには、同じコードをなぞるだけの検査より、
丸め方向、符号拡張、型別の既定値、変換順序で結果が変わる具体例を置きます。
実際の実装と照合して不一致が出たら、刺激・観測・期待値のどこに原因があるかを調べます。

## 5. 本リポジトリにモデルを追加する手順

### 5.1 設計と実装

1. 仕様の出典、既存テスト、既存モデルの対象外事項を確認する。
2. 対象の相互作用、因子と水準、組合せの制約、高次因子群、必須ケースを記載する。
3. 刺激・観測・期待値を設計し、識別できない組合せや未定義の競合を見直す。
4. `generators/<generator>.py`へ`NAME`、`VERSION`、`CHAPTER`、`MODEL`、
   `case_name(row)`、`cases()`を実装する。既存の生成器を雛形にする。
5. `cases()`から`common.Case`のリストを返し、各ケースに出典、独立した期待値、
   `interaction_model`と`interaction_values`を付ける。入力が既知でも、既定値などでXを観測する場合は
   `fourstate=True`にする。生成済みファイルを直接編集しない。
6. [generate.py](../generators/generate.py)へ生成器を登録し、
   [interaction_models.py](../generators/interaction_models.py)の`GENERATORS`と
   `registered()`へ登録する。`SuiteModel`にはパス、利用可能な行、観測の説明を渡す。
7. [回帰テスト](../tools/test_interaction_coverage.py)へ意味上の境界の検査を追加する。
   全対象の射影、必須ケースの保持、選択の決定性は共通検査でも確認する。
8. `python3 generators/generate.py`を実行し、新規のSVと期待出力を生成してから実行確認へ進む。

利用可能な行は、実在するテストと対応させます。既存テストを再利用する場合は全行を保持でき、
新規生成器では選択した行だけを生成できます。意味や期待値を変更するときは、
生成器の`VERSION`とモデルの`version`を見直し、変更理由と再実行範囲を記録してください。

### 5.2 期待値の確認と実行証跡

固定版のIcarus 13.0、Verilator 5.052は、期待値の再現性を確認してoracleを登録する用途です。
VerilatorはX/Zに依存しないケースを対象に、二つのseedで確認します。
kirimasimの開発版検証では実行直前に上流の最新コミットを取得・確認し、
そのコミットからビルドしたバイナリを使い、版を記録します。
固定oracle確認用の版と、最新実装を検証する版は用途が異なります。

`generators/record_oracles.py`は全生成器の登録を更新します。
特に`--verilator`へ部分実行のJSONを渡すと、そこにない既存oracleを`spec`へ戻す可能性があります。
全対象を含む結果を使うか、新規項目だけをレビューしてマージし、既存登録が保持されたことを
確認してください。登録を更新したら`python3 generators/generate.py`でoracleメタデータを再生成し、
入力ハッシュが変わるため結果JSONを再採取します。
古い結果のハッシュを現在の値へ書き換えて再利用してはいけません。

次はモデルを指定して実行し、同じ入力について合否を確認する例です。
リポジトリのルートで、シミュレータのパスを置き換えて実行します。

```python
import subprocess
import sys

models = ["division_context", "dynamic_array_resize"]
select = [sys.executable, "tools/interaction_coverage.py"]
for model in models:
    select += ["--model", model]
tests = subprocess.check_output([*select, "--list-tests"], text=True).splitlines()
receipt = "my-results/cross.json"
run = subprocess.run([
    sys.executable, "tools/run_kirimasim.py",
    "--kirimasim", "/path/to/latest-build/kirimasim", "-j", "8",
    "--json", receipt, *tests,
])
gate = subprocess.run([*select, "--results", receipt, "--require-pass"])
if run.returncode or gate.returncode:
    raise SystemExit(1)
```

複数の結果を検査するときは、一つの`--results`の後ろへJSONを並べます。
各結果は独立に評価され、版や実行回をまたいで部分的な合格を合成しません。

### 5.3 文書・集計・回帰を更新する

モデルの観測、制約、対象外、選択数、仕様解釈、不一致の扱いを検証ガイドへ追記し、
日英READMEのモデル一覧と生成器一覧を更新します。続けて次を実行します。

```sh
python3 generators/generate.py
python3 tools/suite_stats.py --update
python3 tools/suite_catalog.py --update
python3 tools/coverage_depth.py --update --minimum-tests 2
python3 tools/requirement_matching.py --update
python3 tools/behavior_coverage.py --update --require-source-reviewed
python3 tools/interaction_coverage.py --update
python3 -m unittest discover -s tools -p 'test_*.py'
python3 tools/lint_metadata.py
```

保存する実行JSONは`coverage/interaction-results/`へ置いてからクロス集計を更新します。
更新後は対応する`--check`も実行し、CIのCheckを確認します。
`interaction_coverage.py --check`は、計画と生成物・集計が最新であることの検査です。
全モデルの実行が合格していることを要求するゲートは`--require-pass`です。
具体的な不一致・未対応は期待値を緩めず記録し、既存テスト、oracle、過去の証跡が
意図せず変わっていないことも確認します。

### 5.4 有限モデルにしない境界条件を追加する

既存テストとの比較から不足する刺激と観測を特定し、規格に基づく期待値を追加します。
この場合も生成器、出典、独立した期待値、版と実行証跡を残しますが、`MODEL`と
`interaction_model`を形式的に付けてクロスの達成率へ算入しません。
Issue #21では`combination_gap`で候補IDを付け、
[照合台帳](../coverage/combination-gaps.json)に主観測・対照、既存再利用/新規、
観測内容、条項、入力指紋を登録しています。

```sh
python3 tools/combination_gaps.py --list-tests
# 一覧の対象を最新コミットからのビルドで実行し、coverage/combination-results/へJSONを保存
python3 tools/combination_gaps.py --update
python3 tools/combination_gaps.py --check
```

`--list-tests`は台帳に対応付けた全パスを出力します。`--check`は対応するテストの存在と
指紋、レポートの更新状況を確認するもので、実装の全件合格は要求しません。
台帳の入力指紋を変更するときは、刺激・観測・期待値・規格根拠を再レビューします。
規格解釈を確定できない項目は保留し、ネイティブAPIでしか観測できない項目は別の試験範囲として
記録します。未対応を成功の期待値にしたり、未確認の項目を違法や不具合へ読み替えたりしません。

## 6. 何を達成したと数えるか

計画上の網羅、実行での到達、正しい結果まで確認した合格を分けます。
本リポジトリのクロスレポートは、選択計画と**期待値に一致した組合せ**を集計し、
失敗した実行が途中まで到達した生のカバレッジは計測していません。

合格の証跡には、現在の入力ハッシュとランナーハッシュが一致する`pass`だけを使います。
`known`、`unsupported`、`stale`、未実行を合格に含めません。
ランナーが既知の差異を許容して終了コード0を返しても、クロスを達成したとは限りません。
`--require-pass`は、指定した各モデルの全対象組合せと全必須ケースが、
**一つのスナップショット内で**合格することを要求します。
代替する行で対象を満たせる場合もあるため、利用可能なケースの全件合格を要求する仕組みとは
区別します。各ケースの回帰結果も併せて確認します。

ハッシュは入力と実行ツールの取り違えを検出する仕組みです。バイナリが上流の最新コミットから
作られたことや実行環境全体の一致までは証明しません。上流コミットの確認、ビルド、
シミュレータの版・構成・seedの記録を別途行います。

選択数の削減率は実行時間の削減率ではありません。生成、コンパイル、シミュレーションの
所要時間を測り、短時間回帰へ採用する効果を確認します。登録モデルの100%は、
全言語、全仕様、全状態空間、全ての時系列を検証したという意味ではありません。

## 7. 他プロジェクトへ適用する方法

移植するのはSystemVerilog固有の幅一覧より、次の作業のつながりです。
「相互作用の仮説→有限な因子モデル→制約の確認→重点クロス→刺激→実際の観測→独立した判定→証跡」を
一組として管理します。モデルごとに、次を残してください。

- 対象仕様と、どの相互作用の誤りを検出するか。
- 因子・水準・代表値の選定理由、組合せの制約とその根拠。
- 全因子対、重点の高次群、保持する必須シナリオ。
- ケースIDと刺激の生成方法、観測点、期待値または判定器。
- 仕様・実装・テスト・判定器の版、実行構成、結果と未達理由。
- 次に追加する候補と、変更時に無効になる証跡の範囲。

APIなら認証状態×操作×再試行×通信断、ストレージなら書込み×容量境界×障害復旧など、
同じ状態を操作する機能から始めます。これは因子候補の例であり、
本リポジトリで実行・検証したモデルではありません。

### LSIのロジック検証へ適用する場合

FIFOなら占有数（空・1・満杯直前・満杯）、読出し・書込み、バックプレッシャを候補にします。
要求を発行したことと実際に受理されたことを分け、
「操作前の占有数×読出し受理×書込み受理」を重点クロスにします。
満杯時に読出し要求と書込み要求が同時に出た場合の受理条件や、空での動作は、
その設計の仕様から決めます。
深さ1で代表値が重複する場合は整理し、RTLの未対応を除外理由にしません。

DMAなら未完了要求×バックプレッシャ×リセット、割り込みならイベント×W1C×マスクなど、
共有状態と優先順位に効く群を選びます。「Aの前／同時／後」だけで不足する場合は、
受理直前、受理済み未完了、完了直後、中断後の最初の処理を必須シーケンスとして保持します。
到達可能性は初期状態と操作列を含めて確認します。

UVMなどへ実装する場合は、選択した行からシーケンスを起動し、モニターで実際の受理、
事前状態、トランザクションID、クロックドメインと受理サイクルを記録します。
複数クロックでは受理・完了のドメイン、同期遅延、因果関係を定義し、
同じシミュレーション時刻だけで同時と判断しません。同じ相互作用に属する情報をそろえ、
スコアボードやSVAで値、順序、欠落、重複、リセット後の復帰を判定します。
機能カバレッジは小さなクロス、重点クロスを定義したビン、時間関係の目標へ分け、
設定値を指定しただけ、または無関係なトランザクションで各因子を観測しただけで達成としません。
到達と合格を分け、チェッカーが有効で、必要な応答、照合、SVAの評価が完了したことも確認します。
SVAの前件が成立しないままの成功や、スコアボードの照合待ちを合格の根拠にしません。
構成・チャネル・インスタンスごとの不足も保持します。

この資料の方法を具体化した別リポジトリには、
[LSI向けの実施手順](https://github.com/kurochan001/lsi-verification-method/blob/main/docs/method/feature-interaction-verification.md)、
[計画書テンプレート](https://github.com/kurochan001/lsi-verification-method/blob/main/docs/templates/interaction-coverage-plan.md)、
[APB・割り込みの実行可能な教材](https://github.com/kurochan001/lsi-verification-method/blob/main/examples/local-apb-irq-coverage/README.md)
があります。教材の結果は、実製品での採用実績や一般的な削減率を示すものではありません。
クロス検証はサインオフ全体の代替ではなく、CDC/RDC、タイミング、電源などは
それぞれの検証方法と組み合わせます。

## 8. 追加を完了とする基準と、次の拡張

一つのモデルの導入は、刺激と観測の独立レビュー、全対象と必須ケースを保持する選択、
独立した期待値、実行証跡、未達理由、再実行手順、文書からの導線がそろった時点で完了とします。
導入完了と、検証対象の実装が全対象に合格したことは分けて報告します。

不足が見つかったら、まず原因を分類します。未実行なら実行、未対応なら実装課題、
刺激が届かないなら操作列や環境、正誤を識別できないなら刺激・観測・期待値、分母が不適切なら
仕様とモデルのレビューへ戻します。単にランダムseedや高次クロスを増やすことから始めません。

連結した左辺への分割代入と、論理・リダクション演算のX/Zを、この手順で追加した
事例は[検証ガイド](interaction-verification.md)に記載しています。後者は各行で7演算を
観測し、ケース数を抑えながらそれぞれの期待値を確認します。
二項論理演算の短絡評価と副作用、イベント式のエッジ判定も同じ手順で追加しています。
短絡評価は各行で4演算を、イベント制御は各行で背景0/1と3種のイベントを観測します。
背景値を各行のフェーズへまとめることで、因子の直積と選択器の計算量を抑えながら、
両背景と各行の相互作用を確認しています。
Issue #21では副作用を持つ`iff`などの個別の境界条件も追加しています。
次のクロスモデルの候補は、イベントOR・iffの因子モデル化、同一時間ステップ内の複数更新や
グリッチを含む時系列などです。
これらの候補は、この時点で追加済みとする一覧ではありません。
新規不具合や仕様変更から必要性を判断し、今回と同じ手順で観測と証跡まで追加してください。
