# 機能間クロス検証の考え方と実践手順

[English](interaction-verification-method.en.md) / [日本語](interaction-verification-method.md)

この資料は、本リポジトリで機能間クロス検証を導入した際の判断、設計方法、 実装・計測の手順をまとめたものです。新しい項目を追加する担当者と、 別のソフトウェアやLSIのロジック検証へ適用する担当者が再利用できるようにしています。

導入済みモデルの詳細と実行結果は[検証ガイド](interaction-verification.md)、 現在の因子・分母・実行ごとの達成状況は[クロス検証レポート](interaction-coverage.md)、 規格要求とテストの対応付けは[要求からテストを作る手順](requirements-to-tests-method.md)を 参照してください。本資料は方法を説明し、最新の件数はレポートで確認します。 ビルド版と残件を短く読む場合は[保存実行の概要](interaction-verification.md#保存実行の概要)、 固定参照版の不一致は[差異一覧](simulator-differences.ja.md)を参照してください。 有限モデルとは別に追加する境界条件の回帰テストは、 [Issue #21の回帰取り込みレポート](p1-combination-regressions-20261030.md)と [照合台帳](../coverage/combination-gaps.json)で、既存テストの再利用、規格根拠、保留事項を管理します。

<a id="1-design-rationale"></a>

## 1. 設計思想

<a id="verify-boundaries-that-passing-individual-features-cannot-establish"></a>

### 単独機能の合格だけでは分からない境界を検証する

一つずつ正しく動く機能でも、値・状態・型・タイミングを受け渡す境界で不具合が生じます。 例えば、符号付き演算そのものと幅変換そのものが合格していても、 「代入先の幅に広げてから除算する」処理が正しいとは限りません。 NBAも、最終値だけでは値と代入先をいつ確定したかが分かりません。

そこで、機能名を並べることより、**何と何が相互作用し、どの観測で正誤を区別するか**を 先に決めました。モデルの一行には、刺激、観測点、規格から決めた期待値を対応付けます。 テスト内に二つの構文が現れるだけでは、そのクロスを検証したとは扱いません。

<a id="divide-behavior-into-small-semantic-units-before-selecting-combinations"></a>

### 小さな意味単位へ分けてから組合せを選ぶ

全機能の直積は作りません。「演算のコンテキスト」「NBAの値と代入先の確定」 「配列のサイズ変更」など、結果を説明できる単位に分けます。その中で、 制約付きの2因子網羅を基本とし、故障の起こり方に直結する因子群は3因子以上で網羅します。 境界値と既知不具合の再現条件は、組合せが他のケースで代替されても必須ケースとして残します。

この方法は、選んだ低次の相互作用を少ないケースで確認するための設計です。 2因子網羅によって、任意の高次の不具合を検出できるという保証はありません。 モデルに含めていない値・状態・順序にも保証は及びません。

<a id="keep-expected-values-and-denominators-independent-of-implementation-convenience"></a>

### 期待値と分母を実装の都合に合わせない

期待値はIEEE 1800-2023に基づき、検証対象の実装から独立したPythonモデルで計算します。 シミュレータの出力を期待値に写しません。 他のシミュレータとの照合は期待値の確認に使います。食い違った場合は仕様解釈とテストを 再確認し、未対応や不一致も残します。合格率を上げるために対象を除外しません。

既存テストは保持します。短時間実行用の選択を追加することと、通常の回帰テストを 削減することは別です。また、クロスの達成数をそのまま全規格の要求カバレッジへ加算しません。

<a id="2-what-to-model"></a>

## 2. 何をモデル化するか

<a id="prioritize-additional-candidates"></a>

### 追加候補の優先順位

既存テストと仕様を調べ、次の観点で追加する項目を選びます。

- 同じ値や状態を複数の機能が読み書きする。
- 型変換、幅変換、バッファ、階層、引数などの境界を通過する。
- 優先順位、遅延、同時実行、更新前後の違いが結果に影響する。
- 1・32・33・64・65・129ビットなど、実装上の境界をまたぐ。
- X/Z、空、満杯、ゼロ、負数など、通常値と処理が変わる。
- 既知不具合がある、または既存モデルで明示的に対象外としている。

既存テストが同じ刺激と観測を持つ場合は、再利用を先に検討します。 最初の`scheduling_visibility`は既存の325件を保持し、その中から51件を選ぶ方式でした。 新しい刺激が必要な項目では、生成器と独立した期待値を追加しています。

候補すべてを因子モデルへ変換する必要はありません。Issue #21では、イベント、NBA、 複合型、I/Oの境界条件を確認する56件と、ファイル監視の有限モデルから選んだ18件を追加しました。 前者は具体的な境界条件の回帰テストとして台帳へ対応付けます。 後者は登録元の記述位置×キュー/動的配列×MCD/FDの36通りを定義し、 全因子対40組と必須ケース3件を保つ18件を選びます。 因子と対象組合せを定義していない回帰テストの件数を、t-wayの達成数へ加えません。

<a id="choose-factors-and-levels-from-differences-that-affect-results"></a>

### 因子と水準は、結果に影響する違いから決める

因子は幅、符号、格納先の状態型、操作、入力値、時刻などです。 水準はその代表値です。「幅を広げる」のような相対値は、どの幅を基準にするかも定義します。 例えば`state=bit`が入力型を表すのか、最終代入先だけを表すのかで期待値は変わります。

水準を増やす前に、その差を観測できる刺激を用意します。1ビット要素の配列では 一回の0/1パターンだけで複数の位置を区別できないため、入力を巡回させた二回の観測を使いました。 除算のX/Zケースには既知入力も与え、一律Xになる結果だけで符号や幅のクロスを認定することを 避けました。一行が一つの入力ベクトルに限定されるわけではありません。

副作用のある式では、値だけでなく評価回数も観測します。複合シフト代入の40件では、 配列要素や部分選択の添字関数が次の戻り値を変更するようにし、呼出し回数・書込み先・ 非選択領域を同時に確認します。規格上1回の評価を2回にする故障注入でも検出を確認しました。 Verilatorで観測した2回評価を期待値へ取り込まず、差異として保存しています。

4状態の期待値は、2状態の数学的な集合判定へ置き換えないようにします。`inside`では、 比較ごとにXを求めてからORを取ります。例えばXを0/1へ具体化するとどちらも集合に入る場合でも、 二つの比較がともにXなら結果はXです。独立検算でも処理の単位と順序を規格に合わせ、 一致と不明値が混在する必須ケース、同じ要素の個別列挙、先頭要素しか読まない故障注入を使いました。

規格本文の読み方が分かれる組合せでは、どちらの読み方でも同じ結果になる刺激を選び、 残る組合せは理由を付けて制約で除きます。`inside`の範囲指定では、一方の端点がX/Zのとき、 二つの関係を`&&`で結ぶ読み方と、Xの比較があれば範囲をXとする読み方があり得ます。 閉区間では、もう一方の端点を満たす入力だけを使うことで、どちらでもXになるようにしました。 X/Zを含む空の範囲は本文が扱いを定めないため、逆順の範囲は既知値だけにしています。 期待値を片方の読み方へ寄せるのではなく、読み方に依存しない観測で相互作用を確かめます。

観測の仕組みそのものを、全ケースに共通の前提にしないことも大切です。case insideでは、 評価回数を数える関数呼び出しの項目を全ケースに置くと、副作用のある項目が未対応の実装では 全件が未対応になり、幅・符号・X/Zの相互作用を一件も確認できませんでした。 そこで3番目の項目を変数と関数呼び出しの因子に分け、評価回数は関数呼び出しの行で、 選択の規則は両方の行で確かめるようにしました。

イベントORと`iff`では、条件を変える刺激と発火元を変える刺激を別時刻に分け、 左右それぞれの生のイベント数と条件付きORの起床数を並べました。 条件だけの変化での誤起床と、ORの片方の項や条件の結合を失う誤りを区別できます。 全252行の期待値をフェーズごとの計数式で検算し、選択した4行の正の対照条件と、 SVの条件・発火・更新を意図的に誤らせた7種類の故障注入も実行しました。 値の一致だけでなく、起床数や起床しなかった期間も観測対象にする方法です。 追加手順と再実行コマンドは[イベントORの確認記録](interaction-verification.md#イベントorと項ごとのiff条件)と [補助証跡](../coverage/interaction-qualification/README.md#イベントorとiffの確認)を参照してください。

参照を検証するときは、値と位置に加えて「同じ要素か」をモデルに持たせます。 キューではメソッドと全体代入が同じ配列値を作っても、保持中の参照の有効性が異なります。 参照モデルでは要素オブジェクトを移動・置換し、独立検算では位置対応の表を使いました。 初期値を3回巡回させることで、1ビットでも3要素を識別できます。 削除後の参照値と現在のキューの全要素を両方読み、書込み直後と復帰後を分けて観測する方法は、 他のコンテナ、バッファ、識別子の再利用を伴う検証にも応用できます。 具体的な刺激と制約は[キュー参照の確認記録](interaction-verification.md#キュー要素への参照と要素の寿命)を参照してください。

実引数を選ぶ添字の変更は、選ばれた要素自体の変更や削除と分けて扱います。 引数の結合モデルでは、有効な要素を渡してから添字だけを次要素や-1へ変えます。 その後は変更した添字で配列を読まず、すでに結合した対象の値を観測するので、 正しい刺激を無効アクセスにしてしまうことなく、誤った再選択を検出できます。 さらに呼出し元→タスク、タスク→呼出し元、呼出し元の後続更新→タスクの3段階を観測し、 値コピーとライブな参照、即時の書込みと復帰時の誤った書戻しを区別します。 詳細は[引数結合の確認記録](interaction-verification.md#引数の結合と呼出し後の添字変更)を参照してください。

書込みと読込み、符号化と復号のように逆向きの処理を組み合わせる場合は、 仕様から作った既知入力と期待出力を、各方向に用意します。往復結果が元に戻るだけの検査では、 二つの処理で対応する誤りが起きると相殺されるためです。 メモリファイルのモデルでは、DUTが出力したファイルに加え、検証対象の値から整形していない リテラルの入力ファイルも読み込みます。書込みと読込みの両方を逆順にする故障では、 往復側の値が一致していても、独立入力側の値から誤りを検出できました。 同じ考え方は、LSIのエンコーダ/デコーダ、シリアライザ/デシリアライザ、送受信データの照合にも使えます。 具体例は[メモリファイルの確認記録](interaction-verification.md#型と範囲を組み合わせたメモリファイル入出力)を参照してください。

取消しや停止を検証するときは、「停止後に書込みがない」だけでは不十分です。 停止対象がそもそも開始していなかったり、解放する刺激が届かなかったりしても同じ結果になるためです。 program終了のモデルでは、開始直後の進捗、終了前の時刻5のチェックポイント、終了後の書込み抑止を分けて観測します。 同じ遅延・イベント・条件を待つ別programには、解放後の起床を必須とする対照も用意します。 複数initialの自然終了では最後のinitialまで子を存続させ、$exitでは他のinitialと子も取り消す違いを確認します。 LSIのリセットやキューのフラッシュでも、停止前の進捗・停止後の抑止・独立した系統の継続という観測の分け方を適用できます。 具体例は[program終了の確認記録](interaction-verification.md#program終了と子孫プロセスの取消し)を参照してください。

繰返し模様を使う場合は、値の組合せの網羅と、位置の識別を分けて確認します。 net型のモデルでは、解決表を全ビットで通しても16ビット周期の同値性が残りました。 そこでビット位置1〜129を8回の履歴で符号化する刺激を同じ40件へ追加し、 下位ワードを上位へ再利用する故障を、この追加刺激だけで検出することを確認しました。 チャネルやレーン、バッファの要素でも、操作の網羅と識別用のデータを組み合わせる方法を使えます。

接続先を検証するときは、選択側・非選択側の値と識別情報を同時に観測します。 生成したinterfaceのモデルでは、要素とビット位置を表す11回の履歴に、役割を区別する2回を加えました。 これにより反転後も選択側と対照側の履歴が異なり、幅129/130/131の3要素で780個のビット位置を識別できます。 未知値でデータだけの区別が難しい場合にも、要素・分岐ごとのタグからreaderの接続先を照合します。 この方法は、LSIのレーン・バンク選択や、複数インタフェースの接続を検証するときにも適用できます。 具体例は[generateとinterfaceの確認記録](interaction-verification.md#generateで生成したinterfaceとmodport接続)を参照してください。

処理の予約と完了は、別の観測で確認します。programのイベント領域のモデルでは、 moduleのNBA予約回数が増えても、最終段はまだ旧値という固定版の出力を確認しました。 各段の値、予約回数、採取した文脈、後の出力通知を合わせて照合し、早いmodule内の対照も置いています。 非ブロッキング代入の直後と更新後の値を分ける方法は、LSIのパイプラインやキューの 受付・完了、更新通知の検証にも応用できます。 具体例は[programのイベント領域の確認記録](interaction-verification.md#programのイベント領域と非ブロッキング代入)を参照してください。

変換を伴う機能では、既知値で同じ結果になる処理順序を区別する刺激が必要です。 interfaceのモデルでは、package関数のbit型の仮引数へ未知値を変換してから反転する1と、 未知値を反転してからbitへ戻す0を区別します。後者の故障は既知入力11回の出力55行を通過し、 最初の未知入力で初めて検出できました。変換前・格納後・演算後・最終出力を別々に観測し、 後段の処理による誤りの相殺も防いでいます。 名前の結合では、宣言側の既定値と呼出し側の実引数を、意図的に異なる同名宣言で比較します。 再exportする名前も、候補になっているだけでなく実際にimportした宣言か確認します。 LSIのデータ整形・符号/幅変換や設定の結合でも、処理順が結果へ現れる値と中間観測を組み合わせる方法を使えます。 具体例は[型変換とインタフェースのインポート](interaction-verification.md#interfaceヘッダのimportとpackage関数の型変換)を参照してください。

状態保持を検証するときは、出力が変わらない時間だけでなく、入力が変わったのに保持されることを観測します。 逐次UDPのモデルでは、部分集合だけへクロックを与えて非選択側の状態を照合し、 別クロックのguardはデータが変わる間も初期状態を保持させました。 最後にはguardも駆動して位置を識別する値を採取させ、同時にtarget側の保持を確認します。 未知入力の直前には全1を採取させ、型変換後の0やUDPのXが、以前の状態と必ず異なるようにしています。 LSIのバンク・チャネルやクロック/イネーブルで更新する状態でも、非選択時の保持・後の動作・選択側の独立性を 一つの時系列で比較する方法を適用できます。 具体例は[生成した逐次UDPの確認記録](interaction-verification.md#generateで生成した逐次udpの状態と入力変換)を参照してください。

強度や優先順位を検証するときは、単独の値と競合後の値を両方観測します。 UDPのモデルでは、同じ入力の配列を2個置き、一方だけを別ドライバと競合させました。 0・1・Zの切替えにより、指定した強度の違いと解放の動作を論理値で区別でき、強度の表示書式に依存しません。 接続確認用の既知刺激では各ビットの値を識別し、真理値表の確認では全4状態の入力対を与えます。 この二つを同じ行の時系列へまとめ、未知出力と別ドライバの競合は次の独立したモデルの候補として範囲を明示しています。 名前付き配列の要素の同時入替えなど、外部動作が変わらず今回の観測では区別しない範囲も記録します。 LSIのバス駆動や優先度選択でも、単独動作・競合時・解放後を比較し、観測できる粒度を明示する方法を使えます。 具体例は[UDPと強度の確認記録](interaction-verification.md#udpの配列接続と駆動強度の解決)を参照してください。

設定の優先順位とリセットを組み合わせるときは、指定したパラメータだけでなく、 指定しなかったパラメータ・対象外の兄弟・派生した生成形状も観測します。 configのモデルでは、Wだけを戻す操作と全パラメータを戻す操作を分け、事前指定の4種類と交差させました。 各leafは実際に生成した配列を表示するため、生成数の誤りも階層名の欠落ではなく出力差で識別できます。 この重点クロスから、全体リセットとdefparamを併用する4件の差異が見つかりました。 空の全体リセットと、各パラメータを明示したリセットを最小例で比較し、期待値を維持して保存しています。 同じ考え方は、LSIのパラメータ構成、レーン数・バンク数、設定の優先順位やリセット範囲の検証にも使えます。 具体例は[configとgenerateの確認記録](interaction-verification.md#configのパラメータ設定とgenerateの形状)を参照してください。

設定の適用範囲を検証するときは、設定が効く対象・明示指定による例外・設定を戻した後の対象を、同じ刺激で比較します。 default_nettypeのモデルでは、指示の下で定義したmodule、vectorだけを明示wireにしたポート、 既定値へ戻した後に定義したmoduleを並べます。インスタンス化は設定を戻した後に行い、 先に定義したポートの型まで後の設定に置き換わらないことも確認します。 この比較方法は、LSIのパラメータやコンパイル時設定と、インスタンスごとの構成を照合する際にも応用できます。 具体例は[net型とポート宣言の確認記録](interaction-verification.md#default_nettypeとポートnetの解決)を参照してください。

<a id="distinguish-combination-constraints-from-unsupported-tool-features"></a>

### 組合せの制約とツールの未対応を区別する

制約は仕様上成立しない条件と、意味が同じ代表値の重複を除くために使います。 幅1から1ビット狭める幅0や、容量2に対する初期サイズ3などが例です。 空配列で入力値が存在しない場合は、値因子を一つの水準へ固定しました。 除外の理由は生成器とレポートへ記録します。

現在の実装が処理できない、期待値が一致しない、生成が難しいという理由で組合せを除外しません。 仕様違反の入力を拒否する検査は、正常な組合せモデルと区別して設計します。

対象の分母は、**残りの因子を補えば制約を満たす完全な組合せになるもの**から求めます。 因子ごとの水準を機械的に掛けたペア集合を分母にすると、実現不能な組まで不足に数えてしまいます。

DPIのような境界では、同期的な書戻しと、予約して後から反映する更新を分けて観測します。DPI/NBAモデルは復帰直後の全要素、予約後の元値・添字の変更、Postponedと次時刻の値を比べます。即時化・遅い確定・書戻し欠落を別の故障として検出する方法は、LSIのレジスタ書込みと予約済みトランザクションの検証にも応用できます。[具体例と適用限界](interaction-verification.md#dpi-copyback-and-nba-capture)を参照してください。

解を一意にできる制約は、乱数列を固定せずに継承・型・状態のクロスを照合できます。継承制約モデルでは、充足可能と矛盾を交互に与え、初回失敗時の番兵値と成功後の保持値を区別します。別オブジェクトを反対の静的型のハンドルから毎回成功させる対照により、状態の共有や名前解決の混入も観測します。LSIでも失敗する操作の戻り値と状態の保持、独立した対象の進捗を同時に確認する方法へ応用できます。[具体例と適用限界](interaction-verification.md#constraint-inheritance-and-failure-retention)を参照してください。

採取時点と評価時点が異なる場合は、各点のサンプル値と生信号、実行回数を分けます。clocking/assertionモデルは、同じclocking変数を自身のイベントと後続の別クロックから照合し、生信号のassertionを対照にします。時刻をずらして報告することでactionとの競合を避け、再サンプリング・イベントの取り違え・action欠落を別々の故障として確認します。LSIでも、保持した入力と後で変化するバス値を比較するパイプライン検証へ応用できます。[具体例と適用限界](interaction-verification.md#clocking-inputs-and-assertion-clocks)を参照してください。

配列と外部APIの境界では、規格上禁止された組合せと実装の未対応を分けます。DPI open arrayモデルでは、動的配列・キューのoutputを合法集合から除き、合法なinput/inoutの未対応は残します。各呼出しで形状と全要素を照合し、CヘルパーのABIスタブでの検算、シミュレータの解析、実際の受渡しを別の証拠として扱います。LSIでも、DPI参照モデルや可変長トランザクションのサイズ・添字・書戻しを同時に確認する設計へ適用できます。[具体例と適用限界](interaction-verification.md#dpi-open-array-shape-and-copyback)を参照してください。

複製したデータにハンドルが含まれる場合は、格納領域と参照先を別々に観測します。クラス配列モデルでは、配列要素の置換・サイズ変更は浅いコピー間で独立し、要素ハンドル経由のオブジェクト更新は共有されることを確認します。値が同じだけで同一性を判断せず、ハンドル比較・コンストラクタ呼出し回数・保存した参照の再利用を組み合わせます。LSIの検証環境でも、トランザクションやスコアボードの複製で配列データと子オブジェクトの所有を区別する検証へ応用できます。[具体例と適用限界](interaction-verification.md#class-array-storage-and-shared-elements)を参照してください。

<a id="3-how-to-select-a-small-case-set"></a>

## 3. 少ないケースを選ぶ仕組み

[interaction_cover.py](../generators/interaction_cover.py)の`Model`は、次の順で選びます。

1. 全因子の直積を列挙し、`legal`で制約を満たす行を残す。
2. 制約を満たす行から全因子対と指定した高次因子群を取り出し、対象の組合せ集合を作る。
3. `anchors`で指定した必須ケースを先に選ぶ。
4. 未充足の組合せを最も多く埋める行を順に加える。
5. 他の選択行で全対象を満たせる冗長な行を除く。ただし必須ケースは除かない。

因子と水準の順序を固定すれば選択は再現できます。貪欲選択と冗長除去であり、 最小件数の解を保証するアルゴリズムではありません。 現在の実装の列挙上限は、**制約を適用する前の全直積で既定10,000行**です。 超える場合は意味単位や構成を分けます。この値は検証対象の仕様上の制限ではありません。

`groups`には、共有状態・変換順序・優先順位などで同時に効く因子群を指定します。 例えば「幅×状態型×X/Z」「容量×初期サイズ×操作」です。モデルの因子全体を 無条件に高次クロスへ戻すのではなく、リスクと仕様上の根拠から選びます。 3因子で足りない相互作用には、さらに高次の群や明示的な必須シナリオを使います。

選択器だけを試す最小例です。これは実行可能なテストベンチの生成までは行いません。

```python
import sys
sys.path.insert(0, "generators")
from interaction_cover import Model

model = Model(
    "example_word_update",
    (("width", ("1", "32", "33", "64", "65", "129")),
     ("state", ("bit", "logic")),
     ("update", ("blocking", "nba")),
     ("value", ("known", "x", "z"))),
    legal=lambda row: True,
    groups=(("width", "state", "value"),),
    anchors=(("129", "logic", "nba", "z"),),
)
selected = model.select()
assert set(model.anchors) <= set(selected)
assert {t for row in selected for t in model.targets(row)} == set(model.universe())
print(len(model.rows()), len(selected))
```

<a id="4-turn-a-row-into-a-test-that-distinguishes-correct-behavior"></a>

## 4. 一行を、正誤が分かるテストへ変換する

入力、途中の値、最終値を分け、どの段階で誤りが起きたかを判別できるようにします。 隣接要素や非選択ビットの保持、コピー元を変更した後の独立性も必要に応じて観測します。 イベント領域や遅延が関係する場合は、観測時刻と競合の有無を仕様で説明します。 規格が実行順序を定めない競合に、一意の期待値を置いてはいけません。

期待値の計算は、検証対象とは異なる表現で行います。例えば、 ビット列の重み順による部分選択、任意精度整数による演算、配列リストによるコピーを使います。 商・剰余ではPythonとSystemVerilogの負数の丸めの差を明示的に扱いました。 仕様に基づく参照モデルにも誤りはあり得るため、別担当のレビューと別計算法による検算を行います。 本導入で使った独立レビューはAIによるもので、人による承認を意味しません。

参照モデルのユニットテストには、同じコードをなぞるだけの検査より、 丸め方向、符号拡張、型別の既定値、変換順序で結果が変わる具体例を置きます。 実際の実装と照合して不一致が出たら、刺激・観測・期待値のどこに原因があるかを調べます。

<a id="5-add-a-model-to-this-repository"></a>

## 5. 本リポジトリにモデルを追加する手順

<a id="51-design-and-implementation"></a>

### 5.1 設計と実装

1. 仕様の出典、既存テスト、既存モデルの対象外事項を確認する。
2. 対象の相互作用、因子と水準、組合せの制約、高次因子群、必須ケースを記載する。
3. 刺激・観測・期待値を設計し、識別できない組合せや未定義の競合を見直す。
4. `generators/<generator>.py`へ`NAME`、`VERSION`、`CHAPTER`、`MODEL`、 `case_name(row)`、`cases()`を実装する。既存の生成器を雛形にする。
5. `cases()`から`common.Case`のリストを返し、各ケースに出典、独立した期待値、 `interaction_model`と`interaction_values`を付ける。入力が既知でも、既定値などでXを観測する場合は `fourstate=True`にする。生成済みファイルを直接編集しない。
6. [generate.py](../generators/generate.py)へ生成器を登録し、 [interaction_models.py](../generators/interaction_models.py)の`GENERATORS`と `registered()`へ登録する。`SuiteModel`にはパス、利用可能な行、観測の説明を渡す。
7. [回帰テスト](../tools/test_interaction_coverage.py)へ意味上の境界の検査を追加する。 全対象の射影、必須ケースの保持、選択の決定性は共通検査でも確認する。
8. `python3 generators/generate.py`を実行し、新規のSVと期待出力を生成してから実行確認へ進む。
9. [章対の対応付け台帳](../coverage/chapter-interactions.json)に主題章・章対・因子条件を登録する。 [0セルの仕分け](chapter-cross-triage.md)に該当するE/Cエントリがある場合は再確認して外し、 モデル表と仕分け表を更新する。章の同時引用だけからクロスを追加しない。

利用可能な行は、実在するテストと対応させます。既存テストを再利用する場合は全行を保持でき、 新規生成器では選択した行だけを生成できます。意味や期待値を変更するときは、 生成器の`VERSION`とモデルの`version`を見直し、変更理由と再実行範囲を記録してください。

<a id="52-check-expected-values-and-record-execution-evidence"></a>

### 5.2 期待値の確認と実行証跡

固定版のIcarus 13.0、Verilator 5.052は、期待値の再現性を確認してoracleを登録する用途です。 VerilatorはX/Zに依存しないケースを対象に、二つのseedで確認します。 kirimasimの開発版検証では実行直前に上流の最新コミットを取得・確認し、 そのコミットからビルドしたバイナリを使い、版を記録します。 固定oracle確認用の版と、最新実装を検証する版は用途が異なります。

`generators/record_oracles.py`は全生成器の登録を更新します。 特に`--verilator`へ部分実行のJSONを渡すと、そこにない既存oracleを`spec`へ戻す可能性があります。 全対象を含む結果を使うか、新規項目だけをレビューしてマージし、既存登録が保持されたことを 確認してください。登録を更新したら`python3 generators/generate.py`でoracleメタデータを再生成し、 入力ハッシュが変わるため結果JSONを再採取します。 古い結果のハッシュを現在の値へ書き換えて再利用してはいけません。

次はモデルを指定して実行し、同じ入力について合否を確認する例です。 リポジトリのルートで、シミュレータのパスを置き換えて実行します。

```python
import subprocess
import sys

models = ["division_context", "dynamic_array_resize"]
select = [sys.executable, "tools/interaction_coverage.py"]
for model in models:
    select += ["--model", model]
tests = subprocess.check_output([*select, "--list-tests"], text=True).splitlines()
receipt = "my-results/cross.json"
run = subprocess.run([
    sys.executable, "tools/run_kirimasim.py",
    "--kirimasim", "/path/to/latest-build/kirimasim", "-j", "8",
    "--json", receipt, *tests,
])
gate = subprocess.run([*select, "--results", receipt, "--require-pass"])
if run.returncode or gate.returncode:
    raise SystemExit(1)
```

複数の結果を検査するときは、一つの`--results`の後ろへJSONを並べます。 各結果は独立に評価され、版や実行回をまたいで部分的な合格を合成しません。

### 5.4 有限モデルにしない境界条件を追加する

既存テストとの比較から不足する刺激と観測を特定し、規格に基づく期待値を追加します。 この場合も生成器、出典、独立した期待値、版と実行証跡を残しますが、`MODEL`と `interaction_model`を形式的に付けてクロスの達成率へ算入しません。 Issue #21では`combination_gap`で候補IDを付け、 [照合台帳](../coverage/combination-gaps.json)に主観測・対照、既存再利用/新規、 観測内容、条項、入力指紋を登録しています。

```sh
python3 tools/combination_gaps.py --list-tests
# 一覧の対象を最新コミットからのビルドで実行し、coverage/combination-results/へJSONを保存
python3 tools/combination_gaps.py --update
python3 tools/combination_gaps.py --check
```

`--list-tests`は台帳に対応付けた全パスを出力します。`--check`は対応するテストの存在と 指紋、レポートの更新状況を確認するもので、実装の全件合格は要求しません。 台帳の入力指紋を変更するときは、刺激・観測・期待値・規格根拠を再レビューします。 規格解釈を確定できない項目は保留し、ネイティブAPIでしか観測できない項目は別の試験範囲として 記録します。未対応を成功の期待値にしたり、未確認の項目を違法や不具合へ読み替えたりしません。

<a id="6-what-counts-as-achieved"></a>

## 6. 何を達成したと数えるか

計画上の網羅、実行での到達、正しい結果まで確認した合格を分けます。 本リポジトリのクロスレポートは、選択計画と**期待値に一致した組合せ**を集計し、 失敗した実行が途中まで到達した生のカバレッジは計測していません。

合格の証跡には、現在の入力ハッシュとランナーハッシュが一致する`pass`だけを使います。 `known`、`unsupported`、`stale`、未実行を合格に含めません。 ランナーが既知の差異を許容して終了コード0を返しても、クロスを達成したとは限りません。 `--require-pass`は、指定した各モデルの全対象組合せと全必須ケースが、 **一つのスナップショット内で**合格することを要求します。 代替する行で対象を満たせる場合もあるため、利用可能なケースの全件合格を要求する仕組みとは 区別します。各ケースの回帰結果も併せて確認します。

ハッシュは入力と実行ツールの取り違えを検出する仕組みです。バイナリが上流の最新コミットから 作られたことや実行環境全体の一致までは証明しません。上流コミットの確認、ビルド、 シミュレータの版・構成・seedの記録を別途行います。

選択数の削減率は実行時間の削減率ではありません。生成、コンパイル、シミュレーションの 所要時間を測り、短時間回帰へ採用する効果を確認します。登録モデルの100%は、 全言語、全仕様、全状態空間、全ての時系列を検証したという意味ではありません。

<a id="7-apply-the-method-to-other-projects"></a>

## 7. 他プロジェクトへ適用する方法

移植するのはSystemVerilog固有の幅一覧より、次の作業のつながりです。 「相互作用の仮説→有限な因子モデル→制約の確認→重点クロス→刺激→実際の観測→独立した判定→証跡」を 一組として管理します。モデルごとに、次を残してください。

- 対象仕様と、どの相互作用の誤りを検出するか。
- 因子・水準・代表値の選定理由、組合せの制約とその根拠。
- 全因子対、重点の高次群、保持する必須シナリオ。
- ケースIDと刺激の生成方法、観測点、期待値または判定器。
- 仕様・実装・テスト・判定器の版、実行構成、結果と未達理由。
- 次に追加する候補と、変更時に無効になる証跡の範囲。

APIなら認証状態×操作×再試行×通信断、ストレージなら書込み×容量境界×障害復旧など、 同じ状態を操作する機能から始めます。これは因子候補の例であり、 本リポジトリで実行・検証したモデルではありません。

<a id="apply-the-method-to-lsi-logic-verification"></a>

### LSIのロジック検証へ適用する場合

FIFOなら占有数（空・1・満杯直前・満杯）、読出し・書込み、バックプレッシャを候補にします。 要求を発行したことと実際に受理されたことを分け、 「操作前の占有数×読出し受理×書込み受理」を重点クロスにします。 満杯時に読出し要求と書込み要求が同時に出た場合の受理条件や、空での動作は、 その設計の仕様から決めます。 深さ1で代表値が重複する場合は整理し、RTLの未対応を除外理由にしません。

DMAなら未完了要求×バックプレッシャ×リセット、割り込みならイベント×W1C×マスクなど、 共有状態と優先順位に効く群を選びます。「Aの前／同時／後」だけで不足する場合は、 受理直前、受理済み未完了、完了直後、中断後の最初の処理を必須シーケンスとして保持します。 到達可能性は初期状態と操作列を含めて確認します。

UVMなどへ実装する場合は、選択した行からシーケンスを起動し、モニターで実際の受理、 事前状態、トランザクションID、クロックドメインと受理サイクルを記録します。 複数クロックでは受理・完了のドメイン、同期遅延、因果関係を定義し、 同じシミュレーション時刻だけで同時と判断しません。同じ相互作用に属する情報をそろえ、 スコアボードやSVAで値、順序、欠落、重複、リセット後の復帰を判定します。 機能カバレッジは小さなクロス、重点クロスを定義したビン、時間関係の目標へ分け、 設定値を指定しただけ、または無関係なトランザクションで各因子を観測しただけで達成としません。 到達と合格を分け、チェッカーが有効で、必要な応答、照合、SVAの評価が完了したことも確認します。 SVAの前件が成立しないままの成功や、スコアボードの照合待ちを合格の根拠にしません。 構成・チャネル・インスタンスごとの不足も保持します。

この資料の方法を具体化した別リポジトリには、 [LSI向けの実施手順](https://github.com/kurochan001/lsi-verification-method/blob/main/docs/method/feature-interaction-verification.md)、 [計画書テンプレート](https://github.com/kurochan001/lsi-verification-method/blob/main/docs/templates/interaction-coverage-plan.md)、 [APB・割り込みの実行可能な教材](https://github.com/kurochan001/lsi-verification-method/blob/main/examples/local-apb-irq-coverage/README.md) があります。教材の結果は、実製品での採用実績や一般的な削減率を示すものではありません。 クロス検証はサインオフ全体の代替ではなく、CDC/RDC、タイミング、電源などは それぞれの検証方法と組み合わせます。

<a id="8-completion-criteria-and-further-extensions"></a>

## 8. 追加を完了とする基準と、次の拡張

一つのモデルの導入は、刺激と観測の独立レビュー、全対象と必須ケースを保持する選択、 独立した期待値、実行証跡、未達理由、再実行手順、文書からの導線がそろった時点で完了とします。 導入完了と、検証対象の実装が全対象に合格したことは分けて報告します。

不足が見つかったら、まず原因を分類します。未実行なら実行、未対応なら実装課題、 刺激が届かないなら操作列や環境、正誤を識別できないなら刺激・観測・期待値、分母が不適切なら 仕様とモデルのレビューへ戻します。単にランダムseedや高次クロスを増やすことから始めません。

連結した左辺への分割代入と、論理・リダクション演算のX/Zを、この手順で追加した 事例は[検証ガイド](interaction-verification.md)に記載しています。後者は各行で7演算を 観測し、ケース数を抑えながらそれぞれの期待値を確認します。 二項論理演算の短絡評価と副作用、イベント式のエッジ判定も同じ手順で追加しています。 短絡評価は各行で4演算を、イベント制御は各行で背景0/1と3種のイベントを観測します。 背景値を各行のフェーズへまとめることで、因子の直積と選択器の計算量を抑えながら、 両背景と各行の相互作用を確認しています。 Issue #21では副作用を持つ`iff`などの個別の境界条件も追加しています。 イベントORとiffの因子モデル化は、[確認記録](interaction-verification.md#イベントorと項ごとのiff条件)に記載したとおり導入済みです。 次の拡張候補には、同一時間ステップ内の複数更新やグリッチを含む時系列、 逐次UDPの未知クロックや同時入力変化などがあります。 これらは今回の有限モデルの範囲外で、既存テストの有無と対象水準を照合してから追加します。 新規不具合や仕様変更から必要性を判断し、今回と同じ手順で観測と証跡まで追加してください。

<a id="class-handles-and-mailboxes-equal-values-do-not-establish-object-identity"></a>

### classハンドルとmailbox：値が同じでも同一オブジェクトとは限らない

[mailboxとclassハンドルのモデル](interaction-verification.md#mailboxのclassハンドルと別名経由の更新)では、 受け取った値だけでなく、元のハンドルとの同一性、送信元からの更新、受信側からの更新を別々に観測します。 別オブジェクトへ値をコピーした誤実装は、取得直後の値が正しくても、その後の更新が共有されないため識別できます。 さらにFIFO順序、peek/get後の要素数、容量制限とnullを組み合わせ、nullメッセージの成功と空の失敗を区別します。 比較する戻り値は規格に合わせて「正／0」とし、正の値を必ず1とする追加条件は置きません。 空の取得で出力引数がどうなるかも、本文が明示していない条件を期待値へ加えません。

4つの入力系列に最大129ビットずつを与えると、識別対象は516位置です。 位置の2進符号は9回では不足するため10回にし、全0・全1も加えて、反転を含む1,032履歴を区別します。 信号数や幅を増やすときは、既存の刺激パターンの繰返しで別の位置が同じ履歴にならないかを再確認します。 このモデルは3,456通りを36件へ絞り、「幅×状態型×入力」の36組から選択数の下限も説明できます。

独立モデルはオブジェクトと参照、上限付きキューを持ち、生成器の閉形式の並び計算を呼び出しません。 実行未対応の機能は合法な分母に残します。一部の型や既知値で故障注入に成功しても、 別の型やX/Zへ一般化せず、参照版・因子水準・正常終了を確認した範囲を補助証跡に記録します。 導入済みという報告と、対象シミュレータで実行の充足を得たという報告を分ける事例です。

<a id="event-rebinding-separate-copy-registration-and-notification-timing"></a>

### イベントの再結合：コピー・登録・通知の時点を分ける

[イベント再結合のモデル](interaction-verification.md#イベント変数の再結合と登録済み待機の保持)では、 ハンドルをタスクへ渡す時点、`@`が待機先を登録する時点、同期オブジェクトを通知する時点を分けます。 呼出しと登録の間で再結合する刺激により、inputのコピーとref/直接参照の違いを観測できます。 登録後の再結合は既に待つ処理を変更しない、という別の規則も同じ出力で確認します。 各処理を別tickに置くことで、実行順序の競合を仕様差と取り違えません。

後着の待機者、保持した旧ハンドル、独立したnoise、中継ハンドルの変更、複数待機者と未使用スロットを 組み合わせると、同一性の誤り、登録タイミングの誤り、待機キューの共有・混同を区別できます。 これはイベントに限らず、コールバック登録、購読先の変更、接続先の切替でも使える設計手順です。 期待値は時点の選択から閉形式で計算し、独立モデルはオブジェクトと登録キューを順に操作します。

このモデルは合法648通りから27件を選び、必要な27組の3因子群による下限にも達しています。 参照モデル上の13種の誤りに観測差があっても、対象ツールが操作を実行できなければ、 実行での故障検出や組合せの充足とは数えません。構文受理、期待値の独立照合、動作実行、 実行可能な故障注入を、それぞれの根拠と限界に合わせて記録します。
