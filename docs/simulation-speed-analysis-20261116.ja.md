# 遅いベンチの原因と対策の試作（Mac、2026-11-16）

[English](simulation-speed-analysis-20261116.md) / [日本語](simulation-speed-analysis-20261116.ja.md)

大きな差が出た広幅演算では、1 bit ずつ行うシフト・部分選択・連結への書込みが主な負荷でした。ゲート／UDP、メモリ、NBA、待機プロセスには、VM が実行中に繰り返す型の取得・判定と命令処理の負荷があります。word 単位の処理と不変な型情報の事前計算を試作し、広幅は約74%、ゲート／UDPは約19%、メモリは約15%の時間削減を実測しました。

これは別の作業ツリーでの提案用の試作です。正式な simulator main には適用していません。元の [0.1.0 比較](simulation-speed-20261116.ja.md)と、その全13本の測定値は保存したままです。

## 対象と方法

基準は kirimasim 0.1.0 `cfa2ccd75989c1ebb9ed63303271183377364cf0`、Icarus 14.0 devel `1eba3690d8314d79927df8690a7d97642dd93ce0`、Apple M5 Max / macOS 27.2.1 です。試作も同じ release フラグ（`-O3 -DNDEBUG -ffp-contract=off`）で作りました。Mac 手元の simulator main `c152d237` と基準版の `src/vm` / `src/kernel` に差分はありません。Icarus の実装ソースは読んでいません。

正式版6ベンチ、試作3ベンチを macOS `sample` の1 ms間隔で観測しました。割合は計算する worker thread のスタック観測数に対する leaf の比率です。worker の終了を待つ親スレッドは分母から外しています。inline化やサンプリング誤差があるため、厳密なCPU時間の内訳ではありません。profiling時の経過時間は速度比較へ使っていません。

速度は profiling なしで 2026-11-15T22:15:19.418529+00:00〜2026-11-15T22:24:24.534737+00:00（UTC）に再測定しました。1回のn=1 warmup、その後n=1とNを各5回、tool順とn順を交替して直列実行しています。Δは `median(T(N))−median(T(1))`。起動・front-endの完全分離や反復数の比例換算はしていません。開始負荷 [10.73, 12.02, 11.73]、終了負荷 [7.9, 10.05, 10.83]。別のビルドや本調査のテストは同時実行していません。

## 広幅演算の原因

[kernel/wide.cpp](https://github.com/kurochan001/kirimasim/blob/cfa2ccd75989c1ebb9ed63303271183377364cf0/src/kernel/wide.cpp#L396) の `shl`、`ashr`、`bits`、`put` は各ビットを取り出し、A/Bの2面を1 bitずつ書いています。広幅ベンチのworker観測 4,285 回のうち、順に 16.4%、17.2%、14.0%、15.6%、合計 63.2% でした。`operator new` と `mi_free` は合計約 5.8% で、このベンチでは先にビット単位の処理を減らす根拠があります。

試作は4状態のA/B両面を64 bit単位で移動します。シフトは任意幅・符号拡張・X/Z・過大なシフト量を扱い、部分選択とputは64 bit境界に揃う場合だけword処理にして、それ以外は従来の経路を使います。`wide_arith` のΔは正式版 6.598356秒 → word処理のみ 1.828983秒 → 型キャッシュも加えて 1.724225秒でした。割当や4状態を省略せず、大きな短縮が出ています。

## ゲート・メモリ・NBAの原因

[VM の execute](https://github.com/kurochan001/kirimasim/blob/cfa2ccd75989c1ebb9ed63303271183377364cf0/src/vm/vm.cpp#L6374) は各命令でclass・string・realなどの経路を選び、[`typeOf`](https://github.com/kurochan001/kirimasim/blob/cfa2ccd75989c1ebb9ed63303271183377364cf0/src/vm/vm.cpp#L1955) がoperand種別から型表をたどります。型は実行中に変わりませんが、複数の判定で取得し直しています。`typeOf` のleaf観測はゲート／UDP 10.2%、メモリ 9.9%、NBA 14.4% でした。先頭operandの型を全tempの型が決まった後に `InstrInfo` へ保存する試作では、ゲート／UDPの同観測が 1.0%、メモリが 1.1% まで減りました。

UDPの真理値表関数 `udpOutput` 自体はゲートベンチの約 3.3% です。VM命令は227,200,844回、process wakeupは26,000,096回、待機のsubscriptionは38,400,158回。真理値表関数だけの最適化では大きな差を埋めにくく、命令の事前decodeと `waitTriggers` の静的な情報の再構築も次の対象です。

メモリではVM命令192,014,364回、時間の前進8,000,000回、NBA更新24,000,000回でした。大きな配列のコピーが主因という証拠はなく、scalarのロード・ストア、添字、命令dispatch、schedulerの共通コストが積み重なっています。NBAベンチではVM命令1,313,999,693回です。

型キャッシュだけの版を使った追加の3回対照では、word処理込み/型キャッシュのみのΔ比は、ゲートで 1.001、メモリで 1.018 でした。これらは32 bitの経路を使い、広幅変更の寄与は小さく、主に型キャッシュの効果と判断します。3回の記述統計で、同等性の統計的検定ではありません。

## 検証済みの範囲と残る検証

- 広幅の既存valsem照合テスト7件が合格し、境界・符号・X/Z・範囲外選択・in-placeを含む122,184回の追加照合も一致しました。期待値を変更していません。
- 5ケースの計176実行は全て終了正常で、各5回の本測定は期待行と一致し、n=1もtool間で一致しました。追加の型キャッシュ対照も全出力が一致しました。
- 試作は既存12本＋X/Zの1本の全13本で期待出力と一致。比較元の記録がある6本では、全カウンタも一致しました。変わった処理結果やイベントの削減による速度差ではありません。
- simulator全体の `local_ci.py`、sanitizer、実運用の大規模設計の起動時間/RSSは未確認です。real/classを含むVM全体の回帰も正式採用前に必要です。全13本の試作の速度スコアを測ったとは扱いません。

## 対策の優先順位

1. **広幅のword処理**を先行候補にします。今回の大きな差の原因へ直接効いており、公開APIは変えず、unaligned・境界・alias・X/Zの行列を正式な回帰に加えてから採用します。
2. **不変の型情報の事前計算**を小さなVM変更として続けます。先頭operandの型キャッシュは効果を測定済みです。命令ごとに型を保持するため、大規模SIRでのメモリ増加と起動時間も確認します。
3. **型とoperandの位置を事前decodeした命令列**、および静的triggerの構築結果の再利用を検討します。残るgate/UDPの負荷が対象です。効果の数値は未測定。NBA順序、delta cycle、iff、VPI/force、参照とframe寿命を保ち、単純にイベントを飛ばす変更にはしません。
4. word処理後に残る**一時bufferの割当・コピー**を再評価します。試作の広幅profileではnew/freeの比重が上がりました。再入・GC root・tempStackの再確保を考慮したscratch領域の設計が必要です。

## 証跡と再現

基準版をreleaseでビルドし、[word処理パッチ](measurements/2026-11-16/word-ops.patch)と[型キャッシュパッチ](measurements/2026-11-16/type-cache.patch)を別の作業ツリーへ適用すれば試作を再現できます。現在のMac手元mainへの `git apply --check` も通っています。これらは採用提案としての差分です。

[全タイミング](measurements/2026-11-16/prototype-results.json)、[型キャッシュ単独の対照](measurements/2026-11-16/type-only-control.json)、[profile要約](measurements/2026-11-16/profile-summary.json)、[13本の出力とカウンタ](measurements/2026-11-16/prototype-validation.json)、[ビルド・検証情報](measurements/2026-11-16/prototype-provenance.json)を保存しています。[追加の参照照合コード](measurements/2026-11-16/boundary_reference.cpp)は同じ基準版のwide.cpp・valsem/value.cpp・valsem/logic.cppとビルドして実行します。sampleの生ログはマシンの識別情報を含むため非公開保存し、公開要約には関数とworker観測だけを載せています。

## WSL2 での追加確認

[再測定と試作の結果](simulation-speed-wsl2-followup-20261116.ja.md)を `ee544e7f` で受領しました。CPUの内訳はMacでの観測ですが、同じパッチでLinuxの改善も確認できました。全13本の出力と全カウンタが正式版およびMac試作と一致しています。

| ベンチ | Mac 時間削減 | WSL2 時間削減 | WSL2 試作/Icarus |
|---|---:|---:|---:|
| `wide_arith` | 73.87% | 51.36% | 1.223 |
| `gate_udp` | 18.93% | 15.72% | 1.478 |
| `mem_rw` | 14.67% | 14.16% | 1.487 |
| `nba_shift` | 17.09% | 18.57% | 1.102 |
| `proc_wait` | 7.75% | 14.01% | 1.270 |

Linuxの広幅の改善率はMacより小さく、今回の5ケースでは依然Icarusより長い値です。kernel処理・VMの共通コストの改善方向は支持されますが、環境間の差の原因はこの計測だけでは確定しません。
